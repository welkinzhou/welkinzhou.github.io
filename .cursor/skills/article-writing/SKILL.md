# 文章写作与润色

本技能维护跨项目复用的文章表达规范。根据读者、文章目的和作者原有语气选择写法；文件分类、命名、发布格式和站点标题渲染遵循所在项目的约定。

## 按输出格式加载规范

- 先根据目标文件扩展名、用户指定的输出格式和项目约定确定文章载体，不因为技能自身使用 Markdown 就加载 Markdown 规范。
- 目标是 `.md`、`.markdown` 文件，或用户明确要求 Markdown 输出时，读取 [Markdown 文章规范](references/markdown.md)，按当前修改范围应用标题、引用块、列表等规则。
- 目标是 Word、HTML、纯文本等其他格式时，只应用本文件的表达规范，不读取 Markdown 参考；格式未确定时，先完成通用内容工作，确定后再加载对应规范。
- `.mdx` 不直接视为普通 `.md`。明确需要调整其中的 Markdown 正文结构时，再读取 Markdown 参考；JSX、组件、显式 ID 等扩展行为遵循项目约定。
- 只读取当前格式需要的参考文件，不预先加载全部参考。项目对页面标题、元信息和渲染的约定优先于通用格式默认值。

## 理解内容与修改范围

- 改写前读全文；系列文章同时查看相关的前后篇。弄清这段在解释什么、为什么、怎样做、给谁用，以及怎样衔接后文。
- 用户逐段调整时，只完成当前指定范围的修改。其他段落用来理解上下文，不据此重写整篇或整个系列。
- 从作者自然的叙述和用户明确的调整中提取风格，不把偶尔出现的百科腔、重复段落或错字当作偏好。
- 学习笔记保留第一人称、个人判断和未完成的思考；教程根据读者的基础补足解释，不把所有文章都包装成面面俱到的教程。

## 场景、问题与主题

- 开头承接读者已有的知识或当前进度，直接交代为什么看这个东西、遇到了什么问题，或接下来要做什么。
- 问题需要背景时，先交代具体场景：在做什么、原来怎样工作、发生了什么变化、出现了什么现象。让读者知道问题从哪里来，不突然抛出技术疑问。
- 异常出现后，解释它可能怎样发生，补足关键因果。区分已确认的原因与可能原因，不把一种情况写成所有系统的必然行为。
- 场景与问题讲清楚后，再引出文章主题和后续步骤，让读者理解这些步骤与问题的关系。
- 从需求推导方案时，解释为什么需要这种方法、各步骤解决什么问题，以及为什么按这样的关系组织。不要仅列举“这个程序会做什么”，让开发教程读起来像在复述已有项目。设计理由要落在实际需求上，例如先解释为什么模型需要相关文档，再引出 RAG 的检索与生成；用户要求展开时保留这段推导，不用一句功能概述代替。项目复盘或代码解读仍可从已有实现出发，但需区分设计目的与具体实现选择。
- 实践教程沿着业务流程的完善引出技术概念。每一节接住已有结果，说明开发中遇到了什么需求或痛点，再引出解决它的技术方案。技术方案本身就是需求推动下的自然产物，业务与技术共同构成叙述主线，不把二者分成互不关联的功能介绍与术语解析。正文说明当前示例实际实现或模拟了哪些行为，不因标题调整而宣称代码已经完成未实现的功能。
- 介绍统一接口、框架或抽象的价值时，先说明业务中有哪些处理过程，再用同一任务对比直接实现与采用该机制的方式。解释具体减少了哪些调用、组合或维护工作，避免只说“更方便”“统一规范”。简单任务可直接完成，优势随流程和调用需求变化体现；保留数据格式等必要条件，不把接口统一夸大为自动适配所有步骤。
- 系列总纲按从点到面的关系串起各篇：从一个具体步骤开始，说明后面为什么需要补充信息、组合流程或检查结果。每篇的一句话介绍写清“这一章做什么、怎样接住前一步”，避免只堆概念和 API 名称；正文开头承接已有结果，再引出当前问题，体现起承转合。
- 正面说明文章讲什么，不主动罗列“不讲什么”“暂不扩展什么”或无关的技术选项。不在主题内的内容通常无需提及，也不包装成能力或进度的限制；只有会影响读者理解、操作或结论适用范围的边界才需要说明。
- 这些是衔接原则，不是固定开篇模板。已有背景足够时，不补行业趋势；短文可以直接切入，系列文章接住上一篇即可，不反复介绍整套系统。
- 假设场景明确为假设，不虚构作者实际经历。术语在需要时解释，避免开头堆积读者尚不了解的概念。

## 标题与正文

- 主标题和章节标题直接概括主题。已有准确的概念、对象或机制名称时，优先使用原名，英文术语按标准拼写保留，例如 `interrupt`、`Golden Set`、`BM25`；没有合适术语时用简洁的中文主题。不要把技术机制改成含糊的动作描述，也不为追求英文而替换准确的中文名称。
- 标题不承担场景铺垫、提问、执行顺序、次数或结论。例如“写操作前的暂停”用“interrupt”，“一次运行看四项指标”用“评测指标”。这些信息有助于理解时放入正文展开；确有区分主题的需要时，保留“Golden Set 质量”这样的短限定。
- 章节开头说明读者正在处理什么业务、遇到了什么问题、为什么需要本节的方案。假设案例可以来自其他合理业务场景，用“例如”或“设想”交代，不写成作者的真实经历。标题改短后仍要补足这段推导，不能留下只有进度摘要的正文。
- 独立主题需要展开时才设章节。业务步骤可以用“获取用户输入”这样的主题；介绍统一调用或跨步骤共享数据时，用“Runnable”“共享状态”等准确名称。修改前确认标题的范围与正文一致，原标题已经准确时优先修正文中的衔接。

## 自然表达

- 正文沿着问题、尝试、疑问和结果展开。概念在需要时解释，不强套固定章节。
- 非必读的背景和扩展细节保留为选读内容；载体支持折叠时，可以默认收起，减少对正文主线的打断。理解结论或完成操作必需的前提仍在正文直接说明。
- 用直接、具体的动作代替抽象包装，例如“读取文件”“写入数据库”“把上下文拼好”。避免“拿一个小问题把它们用起来”这类指代模糊、搭配生硬的句子。
- 描述连续处理步骤的组合时，优先用“串联”，例如“串联处理步骤”，更直接表达前后衔接、结果依次传递的关系；涉及图的边、分支或其他连接关系时，按实际含义选择用词。
- 引出方法或代码时，检查前文是否已经交代处理需求。例如“用户输入有多余空白”之后，先说明需要去掉或合并哪些空白，再介绍 Python 的处理方法；不直接跳到“先把清理空白写成一个独立函数”。需要补的是现象与方法之间的关系，不是机械增加“我们需要”或套用固定三句模板。
- 从读者理解功能的角度介绍实现，不把作者的编写安排当成解释。“写成独立函数”“封装一下”“拆成几个节点”只有在需要解释复用、接口或流程组织时才展开；否则直接说明这段代码处理什么、为什么用这种方法。命令和操作步骤仍可直接写动作，不为每一步重复铺垫。
- 面向学习者的介绍用能理解的动作和结果，例如“先查资料，再根据资料回答问题”，避免“最小闭环”这类需要读者自行解码的概括。自然表达仍需保持技术区别，不能为了顺口把相关但不同的概念写成同一种东西。
- 多用主动表达，谨慎使用连接词和程度副词，能少用就少用。检查相邻分句是否重复表达时间、顺序或递进关系；关系已清楚时直接叙述，不叠加连接词。事实或需求已明确时，直接陈述，不套“如果……即使……也……”一类假设；条件确实影响结论时再保留条件句。需要推进思路时，可以直接交代场景变化、说明新增需求或提出由此产生的疑问，不把设问当作固定模板。保留表达真实条件、因果和适用范围所必需的词。
- 保留作者原有的“我觉得”“先跑通”“这里容易搞混”，以及合适的比喻、自嘲和少量感叹。真实感来自具体场景和推敲过程，不靠添加语气词。
- 口语化要适度。可以用“看一下”“顺便”“有点麻烦”，不要每段都加“其实”“说白了”“大家都知道”，也不要新增夸张感叹或网络梗。
- 一段讲清一个重点。长句在转折、因果或话题变化处拆开，去掉主谓之间无意义的逗号，不把文章改成碎片化短句。
- 标点按句子关系选择。分号用于确实需要区分层次的并列分句，例如各分句内部已有逗号；简单并列按语意用逗号，独立陈述用句号，不用分号机械拼接相关句子。标题及其紧随的说明避免叠用冒号，例如不写“主题：副标题：介绍”；优先简化标题，必要补充放在括号或独立句中。
- 保留必要的技术术语和代码标识，中文与英文之间留空格，不为口语化牺牲准确性。
- 安装与运行说明直接给出推荐环境、下载入口、初始化命令和执行步骤，再列出手动配置需要满足的版本与服务要求。写读者要怎样操作，不把“本文于某日核对”“示例已完成检查”等助手工作汇报写进正文；验证结果放在交付说明，版本信息只保留对使用代码有帮助的内容。
- 列表用于步骤、配置和并列选项。普通推理保留连贯段落，不为显得完整堆列表、表格和加粗。
- 结尾落在实际结果、尚未解决的问题或下一步；没有必要就直接结束，不补“综上所述”和价值升华。

## 技术内容的支撑

- 讲具体机制时，给出足以理解其行为的代码、伪代码或数据示例。状态流转展示分支与保存点，权限检查展示身份和资源条件，数据结构展示关键字段及其来源，调用流程展示输入、输出和失败处理。只列函数名、接口名或安装命令，不能代替对核心机制的说明；不为纯观点或经验段落凑代码块。
- 代码前承接业务需求，代码后说明关键行为、设计理由和适用边界。保留理解机制必需的检查，不把有副作用或并发约束的流程简化成一条成功路径；也不逐行复述显而易见的代码。
- 引用项目实现时核对源码。讲解用的简化代码、伪代码明确标注，解释省略的初始化、持久化或外部依赖；假设的业务场景可以配教学示例，不将示例说成项目已实现的能力。使用库 API 时确认版本和官方行为。
- 介绍数据对象时，区分核心字段、保证来源与适用范围可追溯的字段，以及辅助排查的字段，解释为什么保留。写评测先交代系统能做什么、质量为何仍未知，再引出标准和评测集。指标除了用途，还要交代范围、单位或换算、方向和读数例子；区分比例、排序分数与相似度，说明均分口径，不把 `0.8` 一概写成“80% 正确”。
- 正文片段与完整代码的关系用简短说明交代：本篇解释什么、完整代码在哪里、运行需要哪些共用文件。不把文件复用关系包装成额外的学习任务。

## 内容与事实边界

- 优化表达，不把润色变成摘要。保留观点、论据、因果、条件、取舍、反例、业务场景和后续用途；篇幅变短不是交付目标。
- 保留支撑结论的例子和推导；技术结构与业务用途要一起保留。自然的段落可以不改，不追求统一句式。
- 合并系列文章时，只整合真正重复的内容。相同概念在不同场景下的推导、约束和结果不是重复；后文保留必要说明与链接，不能只留下“见上一篇”。
- 删除摘要和正文的整段重复；摘要简述本篇问题，正文继续展开。
- 不虚构经历、测试结果、项目进度、数据或情绪，包括为口语感编造“我之前想错了”“越想越乱”。不把“可能”“我猜”改成肯定结论；设想、实际实现和验证结果不能互相替换。
- 删除无依据的“最成熟”“全面领先”等宣传评价；个人体验保留其适用范围，不扩大为普遍定论。
- 不借润色更新历史文章的技术版本。确需修改 API、配置或技术结论时，先核对代码和官方资料，再说明改动；新写的技术内容以当前稳定实现和官方资料为依据。
- 保留原有元信息、链接目标、图片路径、代码与格式结构。修改后逐项核对内容是否完整，修正错字、病句和标记，并按项目要求验证。

## 交付前审核

- 单独检查所有主标题和章节标题：准确术语是否被换成动作描述，是否混入提问、顺序、数量或结论，标题的范围是否与本节一致。不能只审文章主标题。
- 检查每个新概念的入口：读者能否从前面的业务需求理解它为什么出现。已有场景足够时不重复铺垫，没有依据的假设不写成作者经历。
- 检查每个关键机制的支撑：读者能否从片段看清输入、核心判断、输出或状态变化。正文声称的步骤必须在代码中体现或明确说明省略；只有描述和函数名时补足必要示例。
- 核对原文中的理由、约束、取舍、例子和后续用途是否保留，再按载体与项目要求验证。多篇修改完成后统一检查这些项目，不因每篇都有代码块就视为审核通过。

## 从逐段修改中积累偏好

- 用户纠正表达后，先总结问题的共性和改写理由，再将可复用的原则更新到本技能，不只记录替换后的句子。
- 通用表达偏好在本文件维护；Markdown 用法偏好更新 `references/markdown.md` 等对应格式参考。两者共同构成本技能，不再按语言、框架、博客或教程另建相同风格规则。站点目录、命名和渲染要求写入项目规范。
- 更新前检查已有规则和示例。相似问题归纳为同一原则，新偏好与已有内容重合时合并，发生冲突时按用户最新要求修订。只有能说明明显不同的问题、适用条件或改写方法时才新增示例，不为同类问题积累仅换词或换场景的近似示例，也不要求文章重复示例中的句式。

## 改写示例

- 生硬：“可以拿一个小问题把它们用起来：知识库文件已经更新，为什么回答还引用旧内容？”
  自然：先说明学完基础后可以开始实践，再描述知识库助手在部署说明更新后仍按旧步骤回答的场景，解释源文件与检索资料可能未同步，最后引出知识库问答程序的主题。
- 模板腔：“通过对领域模型的深入理解和设计，提高系统的可维护性、可扩展性和可重用性。”
  自然表达：“先把业务规则想清楚，再放进模型里。这样换了数据来源，也不用跟着重写业务逻辑。”
- 生硬：“接下来进行上下文构造，并实现模型调用。”
  自然表达：“接下来把上下文拼好，再传给模型。”
- 突兀：“用户输入可能带有多余空白。先把清理空白写成一个独立函数。”
  自然表达：“用户输入可能带有多余空白，我们需要去掉首尾空白，并把连续空白合并成一个空格。用 Python 就可以完成这一步。”问题在于从现象跳到了编写安排，缺少处理需求，不能仅通过换词或添加口语词解决。
- 口语过头：“这玩意太牛了，直接起飞！！！”
  克制表达：“这个思路挺有意思，先写个简单版本试试。”
