# Markdown 文章规范

仅在目标文章使用 Markdown，或明确需要处理 MDX 中的 Markdown 正文结构时读取。本文维护通用写作用法；站点的标题生成、frontmatter、目录和扩展语法按项目规范处理。

## 标题与章节

- 独立完整文章从一个 H1（`# 文章标题`）开始，正文一级章节用 H2（`##`），子节用 H3（`###`），更细的内容按从属关系继续到 H4、H5、H6。只交付某个段落或章节片段时，沿用所在文章的层级，不另加 H1。
- 文章保持一个主标题。若发布系统已用元信息生成 H1，正文从 H2 开始，不重复写 H1；这是渲染约定的适配，不是把正文章节提升为主标题。
- 同级主题使用同级标题，向下不跳级；结束子节后可以返回上层。不按字号、视觉大小或目录是否展示来选择层级。
- 标题用简短、准确的主题表达，业务环节和技术方案都可以直接作标题，例如“获取用户输入”“共享状态”“LangChain 生态分层”。选题与概括范围遵循技能入口的表达规范，避免“先分清生态里的几层”这类口语化引导。不把整段结论当标题，不用整行加粗代替标题。没有独立章节的短文不必凑出章节。
- 总纲与阅读导航用简短的链接标题，说明放在链接后，避免链接文字内部和外部叠用冒号。例如写 `[Node 与 Runnable](章节路径)：从一个函数开始组织处理步骤`，不写 `[Node 与 Runnable：先把一步写清楚](章节路径)：介绍`。章节页的目的与做法放在开头段落，标题只保留主题。
- 独立主题用章节标题；依附于已有章节的内容用下一级标题，不能为了弱化视觉而跳级。若只是背景补充或外部资源说明，使用普通段落或带明确说明标签的引用块，不强设单独章节，也不为凑层级增加父标题。
- 使用 `#` 形式的标题，标记后留一个空格，标题前后留空行。修改标题时检查重复名称与已有锚点引用。
- 识别标题时跳过代码块和引用示例中的 `#`，不能按行首符号批量修改。

````markdown
# 知识库问答实践

开篇交代场景与文章主题。

## 准备资料

说明这一阶段要完成什么。

### 保留来源信息

说明其中一个具体问题。
````

## 段落与空行

- 连贯叙述、解释和因果推导用普通段落。一段讲清一个重点，不把每句话都拆成一行或一个列表项。
- 段落之间留一个空行；标题、列表、引用块和代码围栏与相邻正文之间留空行。这是保持源文件清楚、减少渲染歧义的写作约定。
- 普通源文件换行不一定产生页面换行。只有诗句、地址等确实需要逐行展示的内容才使用硬换行，不靠 `<br>` 或行末空格组织普通段落。

## 引用块：外部原文与独立补充

- 引用文档、他人的话、需求原文或历史表述时，用 `>` 引用块，让读者区分原文与作者自己的解释；交代来源，外部材料附准确链接。
- 引用保留原意，删节或改动要说明。转述和作者自己的推导用普通段落，不把改写后的话伪装成原文引用。
- 短小、可独立阅读的补充说明也可以用引用块，但需以“说明：”“注意：”等标签明确它是作者补充。支撑正文结论的关键前提放在正文，不藏在补充块里。
- 生态关系、术语辨析或外部资源介绍若只是帮助读者理解正文，可以写成“补充说明：主题”的引用块，并保留相关来源链接。归纳后的说明要明确为作者补充，不冒充外部文档的逐字引文；需要长篇展开时再设简洁的章节标题。
- 不为了左侧竖线、缩进或突出重点而把开场、整段结论、代码及普通叙述都放进引用块。
- 多行引用每行都写 `>`；引用内的段落间用单独的 `>` 空行分隔。避免依赖省略标记的续行行为，引用结束后用空行回到正文。
- 代码、报错与运行日志需要保留格式时使用代码块；若它们属于引用内容，可以在引用块里嵌套代码围栏。

````markdown
需求原文如下：

> 文档更新后，回答需要使用更新后的内容。

这意味着更新流程需要同时处理源文件和检索资料。
````

## 无序列表（ul）：没有先后关系的并列项

- 并列条件、特点、选项、文件职责或检查项使用 ul。判断方法是：交换条目顺序后，意思和执行要求仍然成立。
- 普通列表统一使用 `- `。同一列表的条目保持平行结构，例如都写动作，或都写“名称：作用”，不要混合问题、结论与解释段落。
- 各项需要较长推导时，使用小节或段落展开，不把正文全部塞进项目符号。列表需要引导句时，先交代这些条目在回答什么问题。

````markdown
检索结果需要保留以下信息：

- 文档来源，便于核对原文。
- 内容版本，便于确认资料是否更新。
- 相关片段，作为回答的依据。
````

## 有序列表（ol）：步骤、依赖与明确排序

- 安装流程、执行步骤、阅读路线，以及明确的优先级或排名使用 ol。前一步影响后一步，或读者需要按次序操作时，顺序就是内容的一部分。
- 并列优点、分类和独立建议不使用 ol，避免让编号暗示不存在的先后关系。
- 源文件按 `1.`、`2.`、`3.` 连续编号，便于核对和讨论具体步骤。同一过程内的顺序保持一致；后文引用某一步时同步检查编号。
- 长流程中，每一步先说明动作，再补充目的、输入、结果或命令；复杂步骤可以分成小节，不让编号承担整篇文章的章节结构。

````markdown
更新知识库时，按以下顺序处理：

1. 读取更新后的源文件。
2. 重新整理需要检索的片段。
3. 替换索引中的旧内容。
````

## 列表嵌套与续段

- 只有真实的从属关系才嵌套列表，优先控制在两层以内；层级更深或解释更长时改成小节。
- 子列表、续段和代码围栏缩进到父条目的正文起始列，使用空格。不要机械套用一个固定缩进数，编号位数变化时也要保持归属正确。
- 简短的单段条目不必逐项加空行；条目包含多个段落或代码时，用空行分隔各块，保持同一列表格式一致。
- 可执行的待办事项可以用 `- [ ]`，已完成事项用 `- [x]`，但先确认目标支持任务列表扩展；普通教程步骤不用复选框。

````markdown
1. 准备输入资料。

   - 保留文档来源。
   - 标记内容版本。

2. 执行检索。

   先检查返回的片段，再决定是否生成答案。
````

## 代码、强调与链接

- 函数、变量、命令、参数和路径用行内代码；多行代码、配置、终端输出用围栏代码块，并填写合适的语言标记，如 `python`、`bash`、`json` 或 `text`。
- 展示 Markdown 源码时，外层围栏长于示例中的内层围栏，避免提前结束。代码内容保持原样，不为排版改动命令、缩进或转义。
- 代码前说明要解决什么，代码后解释关键行为。不要把 prose 放进代码块，也不要用代码块代替表格或段落排版。
- 加粗用于少量关键判断或必须注意的条件，不整段加粗，不把每个术语都标为重点；行内代码用于标识，不能代替语义强调。
- 链接使用能说明目标的文字，来源链接靠近对应论述。站内路径按项目约定处理；标题、文件或目录变化时检查链接与锚点。
- 图片填写有意义的替代文字，必要时在图后说明结论与来源。保留已有资源路径，不用作者机器上的临时绝对路径作为发布链接。

## 表格与扩展语法

- 信息需要按相同维度逐项对照时才使用表格，并先确认目标支持表格扩展。长解释和因果推导用段落，步骤用 ol，普通并列项用 ul。
- 表格保持列名清楚、单元格简短；移动端过宽时拆分内容，不把大段文字或代码放进单元格。
- 任务列表、脚注、删除线、提示框、Mermaid 和 MDX 组件不假定所有 Markdown 渲染器都支持；按目标平台和项目约定使用，不把平台扩展当作通用必备格式。
- 目标平台支持折叠时，非必读的背景、生态介绍和扩展细节可以默认收起，摘要用简洁主题并标明“选读”；必读步骤和关键条件不折叠。具体折叠语法与样式按项目规范处理。
- 已有 frontmatter、注释标记、显式 ID 和发布分隔符要保留；普通独立 Markdown 不擅自增加某个站点专用的元信息。

## 修改后核对

- 主标题来源明确，章节从属关系正确，无向下跳级或重复 H1；片段修改保持原文章层级。
- 引用与作者解释分得清楚；列表类型表达真实关系，嵌套、续段和代码归属正确。
- 围栏、引用和强调标记闭合，链接、图片与锚点有效，扩展语法得到目标支持。
- 按项目要求预览或构建；本规范文件本身的修改只检查 Markdown 结构、引用和差异。

语法核对依据：[CommonMark 规范](https://spec.commonmark.org/0.31.2/)、[GitHub 基础格式说明](https://docs.github.com/en/get-started/writing-on-github/getting-started-with-writing-and-formatting-on-github/basic-writing-and-formatting-syntax)。单一主标题、列表选择、引用用途和空行风格是本技能的写作约定，不宣称它们都是解析器的强制语法要求。
