# Vue 响应式

本文先沿着本系列使用的 Vue 3.2 源码分析，补充部分以 [v3.2.47](https://github.com/vuejs/core/tree/v3.2.47/packages/reactivity/src) 为基准。代码片段省略了部分类型和调试分支，重点看依赖如何收集、清理和触发。末尾单独对照当前稳定版 [Vue 3.5.43](https://github.com/vuejs/core/releases/tag/v3.5.43) 的实现，版本确认于 2026-10-07。

Vue 响应式机制使用了观察者模式。数据变化后，Vue 通知依赖这份数据的副作用（effect）。`Dep` 保存这些订阅关系，组件渲染、计算属性和侦听器都建立在这套机制上。

实现方式上，Vue 2 使用 `Object.defineProperty` （重写对象**属性**的 getter 和 setter 方法），Vue 3 使用的是 `Proxy`，都是针对对象。JavaScript 并不能直接检测到变量的变化，只能劫持对象操作。Object.defineProperty 最大的问题是，代理的是对象上的属性，例如 `obj.a` 的读取和设置，不能拦截到 obj 的新增或删除属性。Proxy 中做了更完整的代理，常用的有 get（获取属性）、set（设置属性，包括新增和修改）、deleteProperty（删除属性）。

Proxy 基本使用：

```js
let temp = 1
temp = 2 // js 没有提供机制检测这种修改

let val = "aa"
const obj1 = {
  a: val,
};
// 代理 obj1 中属性 a
Object.defineProperty(obj1, "a", {
  get() {
    getterHandler() // do something
    // 不能直接获取 obj1.a
    // 会再次触发 getter
    return val;
  },
  set(newValue) {
   if(val !== newValue){
     setterHandler() // do something
     // 直接设置 obj1.a
     // 会重复触发 setter
     val = newValue
   };
  },
  enumerable: true,
  configurable: true,
});

const obj2 = {
  a: "aa",
};

const proxyObj = new Proxy(obj2, {
  get(target, key, receiver) {
    console.log('getter', key)
    getterHandler() // do something
    return Reflect.get(target, key, receiver);
  },
  // 即使新增 key 也能检测到
  // 代理针对的是对象
  set(target, key, value, receiver) {
    // 严格模式下返回 false 会报错
    setterHandler() // do something
    return Reflect.set(target, key, value, receiver);
  },
});
```

使用 Object.defineProperty，我们操作的就是原数据，为了避免重复触发 getter 和 setter，每个属性需要映射一个值。而 proxy 会返回一个代理对象，开发者操作修改的是代理对象。代理对象本身并不存储值，只是拦截操作做额外处理，最后使用 `Reflect` 将操作反射到 target 上。上面注释的 do something 就是可以实现响应式的地方，响应式数据需要做额外处理，性能上有损耗，实践中不能无脑使用响应式。这样我们的工作就涉及几步：

* 分析响应式使用的场景。
* 设置响应式数据源。
* 设置响应式数据改变后的回调。

后面两点，实现上要比示例复杂。

先来看一段代码：

```js
const test = ref(22)

console.log('set up', test.value)

setTimeout(() => {
  test.value = 33
  console.log('value changed', test.value)
}, 1000)

testChange() // 调用方法，
function testChange() {
  console.log('inner test', test.value)
}
// 最终结果 
// set up 22
// inner test 22
// value changed 33
// 没有调用 testChange
```

这段代码只调用了一次 `testChange`。1 秒后 `test.value` 变成 33，Vue 并不知道要重新调用哪个函数。我们还需要把数据和更新操作关联起来，普通函数读取响应式数据不会自动成为订阅者。

开发角度考虑，将定义响应式和更新操作收集解耦，是很重要的。功能开发，经常是迭代累加的。一个基础数据，后续可能添加各种功能。这里就需要一种机制，检测到当前需要收集的更新操作。

如何做到这一点，Vue 官网有基础示例：

```js
function reactive(obj) {
  return new Proxy(obj, {
    get(target, key) {
      // 获取位置，追踪依赖
      track(target, key)
      return target[key]
    },
    set(target, key, value) {
      target[key] = value
      // 修改时触发更新
      trigger(target, key)
      return true
    }
  })
}

function ref(value) {
  const refObject = {
    get value() {
      track(refObject, 'value')
      return value
    },
    set value(newValue) {
      value = newValue
      trigger(refObject, 'value')
    }
  }
  return refObject
}
```

effect 运行时读取响应式数据，getter 把当前 effect 记录为订阅者。setter 修改数据后，Vue 通知这些订阅者。effect 可以更新页面，也可以执行其他逻辑，并不只负责渲染。

流程分三步：运行 effect，读取数据并建立订阅；修改数据，通知订阅者；重新运行 effect，更新订阅关系。

第三步重新收集 dep 很重要，不要以为这和第一步重复了。假设有这样一个 effect：

```js
const state = reactive({ enabled: true, text: 'hello' })

effect(() => {
  console.log(state.enabled ? state.text : '关闭')
})

state.enabled = false // 重新执行，只读取 enabled
state.text = 'world' // text 已经没有这个订阅者，不再执行 effect
```

第一次执行，effect 读取 `enabled` 和 `text`。`enabled` 变成 false 后，effect 再次运行，只读取 `enabled`。Vue 在这次运行结束时移除它对 `text` 的订阅，后续修改 `text` 不会触发这个 effect。清理发生在重新运行时，不需要等 `text` 再改一次。

## ref 和 reactive

Vue 中常用的响应式 API 包括 ref 和 reactive 两种，直接看源码实现。

### ref

```ts
export function ref(value?: unknown) {
  return createRef(value, false)
}
function createRef(rawValue: unknown, shallow: boolean) {
  // 重复创建拦截
  if (isRef(rawValue)) {
    return rawValue
  }
  return new RefImpl(rawValue, shallow)
}
// Ref class
class RefImpl<T> {
  private _value: T // 保存的值
  private _rawValue: T // 保存的原始值，响应式变量的 target

  public dep?: Dep = undefined // 订阅列表
  public readonly __v_isRef = true

  constructor(value: T, public readonly __v_isShallow: boolean) {
    this._rawValue = __v_isShallow ? value : toRaw(value)
    // Object 会转成 reactive
    this._value = __v_isShallow ? value : toReactive(value)
  }
	// get 关键字定义 getter
  get value() {
    // 收集依赖
    trackRefValue(this)
    // 返回值
    return this._value
  }
	// set 关键字定义 setter
  // value 是属性名
  set value(newVal) {
    const useDirectValue = this.__v_isShallow || isShallow(newVal) || isReadonly(newVal)
    newVal = useDirectValue ? newVal : toRaw(newVal)
    // 使用 Object.is 判断是否修改值
    if (hasChanged(newVal, this._rawValue)) {
      this._rawValue = newVal
      // 判断是否 shallowRef，shallowRef 不做深层递归代理
      this._value = useDirectValue ? newVal : toReactive(newVal)
      // 触发更新
      triggerRefValue(this, newVal)
    }
  }
}

export function trackRefValue(ref: RefBase<any>) {
  // 当前变量是否需要收集，是否有运行中的 effect
    // shouldTrack 控制是否收集依赖，例如数组修改方法会暂停收集
  if (shouldTrack && activeEffect) {
    // ref 本身也可能被 reactive 或 readonly 包装
    // toRaw 去掉外层代理，让依赖始终保存在原始 ref 上
    ref = toRaw(ref)
    if (__DEV__) {
      trackEffects(ref.dep || (ref.dep = createDep()), {
        target: ref,
        type: TrackOpTypes.GET,
        key: 'value'
      })
    } else {
      // 默认创建一个新的 dep
      trackEffects(ref.dep || (ref.dep = createDep()))
    }
  }
}

export function triggerRefValue(ref: RefBase<any>, newVal?: any) {
  ref = toRaw(ref)
  if (ref.dep) {
    if (__DEV__) {
      triggerEffects(ref.dep, {
        target: ref,
        type: TriggerOpTypes.SET,
        key: 'value',
        newValue: newVal
      })
    } else {
      triggerEffects(ref.dep)
    }
  }
}
```

ref 用 `_rawValue` 比较新旧值，用 `_value` 保存对外返回的值。普通对象会经 `toReactive` 转成响应式对象；shallowRef 和已经具有 shallow、readonly 语义的值直接保留。setter 通过 `Object.is` 判断变化，值没变就不通知订阅者。`trackRefValue` 和 `triggerRefValue` 封装了通用的依赖操作，后面再看。

### reactive

```ts
// 会将生成的 reactive 全部用 WeakMap 保存起来
// key 是 target 被代理对象
// proxy 可以获取到当前访问的 target
// 找到对应的 reactive 对象
export const reactiveMap = new WeakMap<Target, any>()

export function reactive(target: object) {
  // if trying to observe a readonly proxy, return the readonly version.
  if (isReadonly(target)) {
    return target
  }
  return createReactiveObject(
    target,
    false, // 是否只读，闭包保存
    mutableHandlers,
    mutableCollectionHandlers,
    reactiveMap
  )
}

function createReactiveObject(
  target: Target,
  isReadonly: boolean,
  baseHandlers: ProxyHandler<any>,
  collectionHandlers: ProxyHandler<any>,
  proxyMap: WeakMap<Target, any>
) {
  // 简单类型不能做响应式处理
  if (!isObject(target)) {
    if (__DEV__) {
      console.warn(`value cannot be made reactive: ${String(target)}`)
    }
    return target
  }
  // target is already a Proxy, return it.
  // exception: calling readonly() on a reactive object
  if (
    target[ReactiveFlags.RAW] &&
    !(isReadonly && target[ReactiveFlags.IS_REACTIVE])
  ) {
    return target
  }
  // target already has corresponding Proxy
  const existingProxy = proxyMap.get(target)
  if (existingProxy) {
    return existingProxy
  }
  // only a whitelist of value types can be observed.
  // 判断是否为合法的响应式数据源类型
  const targetType = getTargetType(target)
  if (targetType === TargetType.INVALID) {
    return target
  }
  const proxy = new Proxy(
    target,
    // 判断数据源类型，适用不同的 handlers
    // Object Array 使用 baseHandlers
    // Map Set WeakMap WeakSet 使用 collectionHandlers
    // 这两类数据访问自身属性形式不一样，做了区分
    targetType === TargetType.COLLECTION ? collectionHandlers : baseHandlers
  )
  // 保存 map
  proxyMap.set(target, proxy)
  return proxy
}
```

接下来是重点，代理对象的 get、set 方法。Object 和 Array 可以直接读取、设置属性，例如 `arr[0] = 1`。Map 和 Set 通过实例方法操作数据，例如 `map.delete(key)`、`map.set(key, value)`，Vue 在 get 中返回包装过的方法。先看最常用的 Object 和 Array：

```ts
export const mutableHandlers: ProxyHandler<object> = {
  get,
  set,
  deleteProperty,
  has,
  ownKeys
}
// has 和 ownKeys 比较简单，就是代理操作，同时追踪收集依赖
function has(target: object, key: string | symbol): boolean {
  const result = Reflect.has(target, key)
  if (!isSymbol(key) || !builtInSymbols.has(key)) {
    // track 后面两个参数用于 dev 展示调试信息
    // 整个 track 方法后面再看
    track(target, TrackOpTypes.HAS, key)
  }
  return result
}

function ownKeys(target: object): (string | symbol)[] {
  track(target, TrackOpTypes.ITERATE, isArray(target) ? 'length' : ITERATE_KEY)
  return Reflect.ownKeys(target)
}
// deleteProperty 删除属性，需要触发更新
function deleteProperty(target: object, key: string | symbol): boolean {
  const hadKey = hasOwn(target, key)
  const oldValue = (target as any)[key]
  const result = Reflect.deleteProperty(target, key)
  if (result && hadKey) {
    trigger(target, TriggerOpTypes.DELETE, key, undefined, oldValue)
  }
  return result
}
```

接下来看 getter，getter 是 `createGetter` 返回的一个闭包方法：

```ts 
// 所有普通 reactive 对象共用同一个 get 方法
// 避免每个对象新建一个闭包占用内存
// 通过闭包也保存了共有的 isReadonly shallow 信息
function createGetter(isReadonly = false, shallow = false) {
  return function get(target: Target, key: string | symbol, receiver: object) {
    // 特殊属性的代理
    // 体现 proxy 特点，可以访问 target 中没有的属性
    if (key === ReactiveFlags.IS_REACTIVE) {
      return !isReadonly
    } else if (key === ReactiveFlags.IS_READONLY) {
      return isReadonly
    } else if (key === ReactiveFlags.IS_SHALLOW) {
      return shallow
    } else if (
      key === ReactiveFlags.RAW &&
      receiver ===
        (isReadonly
          ? shallow
            ? shallowReadonlyMap
            : readonlyMap
          : shallow
          ? shallowReactiveMap
          : reactiveMap
        ).get(target)
    ) {
      return target
    }

    const targetIsArray = isArray(target)
		// 数组方法重写
    if (!isReadonly && targetIsArray && hasOwn(arrayInstrumentations, key)) {
      return Reflect.get(arrayInstrumentations, key, receiver)
    }

    const res = Reflect.get(target, key, receiver)
		// 不需要代理的属性，有一些 builtin 方法，也需要获取属性对比
    // 这部分不涉及视图更新
    if (isSymbol(key) ? builtInSymbols.has(key) : isNonTrackableKeys(key)) {
      return res
    }

    if (!isReadonly) {
      // 追踪数据
      track(target, TrackOpTypes.GET, key)
    }

    if (shallow) {
      // 浅层代理，直接返回，无需递归
      return res
    }

    if (isRef(res)) {
      // ref unwrapping - does not apply for Array + integer key.
      const shouldUnwrap = !targetIsArray || !isIntegerKey(key)
      return shouldUnwrap ? res.value : res
    }

    if (isObject(res)) {
      // Convert returned value into a proxy as well. we do the isObject check
      // here to avoid invalid value warning. Also need to lazy access readonly
      // and reactive here to avoid circular dependency.
      // 默认将内部访问数据，也会转换成响应式
      // 也就是获取时再转换，定义时不会转换
      // reactive 中没有使用的属性不会转换成响应式
      return isReadonly ? readonly(res) : reactive(res)
    }

    return res
  }
}

// 重写的数组方法
function createArrayInstrumentations() {
  const instrumentations: Record<string, Function> = {}
  // instrument identity-sensitive Array methods to account for possible reactive
  // values
  // 查找时，可能会有响应式数据，在原数据中是查找不到的
  // 需要做额外处理
  ;(['includes', 'indexOf', 'lastIndexOf'] as const).forEach(key => {
    instrumentations[key] = function (this: unknown[], ...args: unknown[]) {
      const arr = toRaw(this) as any
      for (let i = 0, l = this.length; i < l; i++) {
        track(arr, TrackOpTypes.GET, i + '')
      }
      // we run the method using the original args first (which may be reactive)
      const res = arr[key](...args)
      if (res === -1 || res === false) {
        // if that didn't work, run it again using raw values.
        return arr[key](...args.map(toRaw))
      } else {
        return res
      }
    }
  })
  // instrument length-altering mutation methods to avoid length being tracked
  // which leads to infinite loops in some cases (#2137)
  // 改变数组长度的方法，内部可能会获取数组长度，形成 infinite loops
  ;(['push', 'pop', 'shift', 'unshift', 'splice'] as  const).forEach(key => {
    instrumentations[key] = function (this: unknown[], ...args: unknown[]) {
      // 暂停依赖收集
      pauseTracking()
      const res = (toRaw(this) as any)[key].apply(this, args)
      // 恢复
      resetTracking()
      return res
    }
  })
  return instrumentations
}
```

setter：

```ts
function createSetter(shallow = false) {
  return function set(
    target: object,
    key: string | symbol,
    value: unknown,
    receiver: object
  ): boolean {
    let oldValue = (target as any)[key]
    // readonly 属性修改拦截，readonly 数据不能直接修改
    if (isReadonly(oldValue) && isRef(oldValue) && !isRef(value)) {
      return false
    }
    if (!shallow) {
      // 展平数据
      if (!isShallow(value) && !isReadonly(value)) {
        value = toRaw(value)
        oldValue = toRaw(oldValue)
      }
      // 非数组属性原来保存的是 ref，新值不是 ref 时
      // 写入已有 ref.value，保留这个 ref
      if (!isArray(target) && isRef(oldValue) && !isRef(value)) {
        oldValue.value = value
        return true
      }
    } else {
      // in shallow mode, objects are set as-is regardless of reactive or not
    }
		// 是否有对应 key
    const hadKey =
      isArray(target) && isIntegerKey(key)
        ? Number(key) < target.length
        : hasOwn(target, key)
    const result = Reflect.set(target, key, value, receiver)
    // don't trigger if target is something up in the prototype chain of original
    if (target === toRaw(receiver)) {
      if (!hadKey) {
        // 不存在为新增
        trigger(target, TriggerOpTypes.ADD, key, value)
      } else if (hasChanged(value, oldValue)) {
        // 存在为修改
        trigger(target, TriggerOpTypes.SET, key, value, oldValue)
      }
    }
    return result
  }
}
```

以上就是 Vue 在属性劫持中做的额外处理。

Map、Set 对应的方法在 `collectionHandlers.ts` 中，只劫持了 getter，getter 中对调用方法做了处理，值得注意的是 `keys()`、`values()` 等方法，需要手动创建迭代器。

### track 和 trigger 逻辑

ref 中使用的是 `trackEffects` 和 `triggerEffects`，reactive 则使用了 `track` 和 `trigger` 方法。来到 `effect.ts` 文件中，会发现 `track` 和 `trigger` 是对 `trackEffects` 和 `triggerEffects` 方法的二次封装：

```ts
export function track(target: object, type: TrackOpTypes, key: unknown) {
  // shouldTrack 标识是否需要追踪，如上面所示
  // 有些操作需要暂停收集，例如数组修改方法内部读取 length
  // 不能把这个内部读取也当成用户 effect 的依赖
  if (shouldTrack && activeEffect) {
    let depsMap = targetMap.get(target)
    if (!depsMap) {
      targetMap.set(target, (depsMap = new Map()))
    }
    let dep = depsMap.get(key)
    if (!dep) {
      // Dep 本身是一个 Set 增加了两个标识位
      // w 标识是否已被追踪
      // n 标识新增的 dep
      depsMap.set(key, (dep = createDep()))
    }

    const eventInfo = __DEV__
      ? { effect: activeEffect, target, type, key }
      : undefined

    trackEffects(dep, eventInfo)
  }
}

export function trigger(
  target: object,
  type: TriggerOpTypes,
  key?: unknown,
  newValue?: unknown,
  oldValue?: unknown,
  oldTarget?: Map<unknown, unknown> | Set<unknown>
) {
  const depsMap = targetMap.get(target)
  if (!depsMap) {
    // never been tracked
    return
  }

  let deps: (Dep | undefined)[] = []
  if (type === TriggerOpTypes.CLEAR) {
    // collection being cleared
    // trigger all effects for target
    deps = [...depsMap.values()]
  } else if (key === 'length' && isArray(target)) {
    depsMap.forEach((dep, key) => {
      // 数组长度修改，超出长度的都需要舍弃
      if (key === 'length' || key >= (newValue as number)) {
        deps.push(dep)
      }
    })
  } else {
    // schedule runs for SET | ADD | DELETE
    if (key !== void 0) {
      deps.push(depsMap.get(key))
    }

    // also run for iteration key on ADD | DELETE | Map.SET
    switch (type) {
      case TriggerOpTypes.ADD:
        if (!isArray(target)) {
          deps.push(depsMap.get(ITERATE_KEY))
          if (isMap(target)) {
            deps.push(depsMap.get(MAP_KEY_ITERATE_KEY))
          }
        } else if (isIntegerKey(key)) {
          // new index added to array -> length changes
          deps.push(depsMap.get('length'))
        }
        break
      case TriggerOpTypes.DELETE:
        if (!isArray(target)) {
          deps.push(depsMap.get(ITERATE_KEY))
          if (isMap(target)) {
            deps.push(depsMap.get(MAP_KEY_ITERATE_KEY))
          }
        }
        break
      case TriggerOpTypes.SET:
        if (isMap(target)) {
          deps.push(depsMap.get(ITERATE_KEY))
        }
        break
    }
  }

  const eventInfo = __DEV__
    ? { target, type, key, newValue, oldValue, oldTarget }
    : undefined

  if (deps.length === 1) {
    if (deps[0]) {
      if (__DEV__) {
        triggerEffects(deps[0], eventInfo)
      } else {
        triggerEffects(deps[0])
      }
    }
  } else {
    const effects: ReactiveEffect[] = []
    for (const dep of deps) {
      if (dep) {
        // dep 本质是一个 Set，保存 effects
        // 展开后就是 effects
        // 合并通知列表时，只需要这些 effect，并用新 Set 去重
        // 原始 dep 的 w、n 仍用于运行前后的依赖清理
        effects.push(...dep)
      }
    }
    if (__DEV__) {
      triggerEffects(createDep(effects), eventInfo)
    } else {
      triggerEffects(createDep(effects))
    }
  }
}
```

再看一下基础的方法：

```ts
export function trackEffects(
  dep: Dep,
  debuggerEventExtraInfo?: DebuggerEventExtraInfo
) {
  // 默认 false 重复拦截
  let shouldTrack = false
  if (effectTrackDepth <= maxMarkerBits) {
    if (!newTracked(dep)) {
      dep.n |= trackOpBit // set newly tracked
      // 新增的依赖需要加入当前 effect
      // 如果已经添加过，即 wasTracked 无需多次添加
      shouldTrack = !wasTracked(dep)
    }
  } else {
    // Full cleanup mode.
    shouldTrack = !dep.has(activeEffect!)
  }

  if (shouldTrack) {
    // 添加依赖
    dep.add(activeEffect!)
    activeEffect!.deps.push(dep)
    if (__DEV__ && activeEffect!.onTrack) {
      activeEffect!.onTrack(
        Object.assign(
          {
            effect: activeEffect!
          },
          debuggerEventExtraInfo
        )
      )
    }
  }
}

export function triggerEffects(
  dep: Dep | ReactiveEffect[],
  debuggerEventExtraInfo?: DebuggerEventExtraInfo
) {
  const effects = isArray(dep) ? dep : [...dep]
  // 先使 computed 失效，再通知普通 effect
  for (const effect of effects) {
    if (effect.computed) triggerEffect(effect, debuggerEventExtraInfo)
  }
  for (const effect of effects) {
    if (!effect.computed) triggerEffect(effect, debuggerEventExtraInfo)
  }
}

function triggerEffect(
  effect: ReactiveEffect,
  debuggerEventExtraInfo?: DebuggerEventExtraInfo
) {
  if (effect !== activeEffect || effect.allowRecurse) {
    if (__DEV__ && effect.onTrigger) {
      effect.onTrigger(extend({ effect }, debuggerEventExtraInfo))
    }
    if (effect.scheduler) {
      effect.scheduler()
    } else {
      effect.run()
    }
  }
}
```

### 总结

整理一下，reactive 和 ref 的响应式逻辑。

ref 用 `RefImpl` 的 `.value` getter、setter 拦截访问，既能保存基本类型，也能保存对象。reactive 用 Proxy 拦截对象操作，`reactiveMap` 缓存原对象到代理的映射。同一个原对象重复调用 reactive，会得到同一个代理。深层对象在读取时再转换，Vue 不会在创建代理时递归遍历整棵对象树。

reactive 的 ReactiveFlags 也体现了 Proxy 的特点。它们不需要实际写入原对象，Vue 在 get 中拦截这些特殊键，再返回对应信息。开发者工具展示的 target、handler 是代理的内部信息，不是对象上新增的普通属性。

reactive 在 track 处理中，会创建 `target -> key -> dep` 的链条，dep 中有保存相关的 effects。这里有两种 map，`KeyToDepMap` 保存 target 属性到 dep 的映射关系，`targetMap` 存放 target 到 KeyToDepMap 的映射。targetMap 使用 WeakMap，某个 target 被 GC 清理后，WeakMap 中的键引用将不存在，相应值（KeyToDepMap）没有额外引用，也会被清理。dep 是一个 Set，track 过程会将当前正在运行的 effect（activeEffect）添加进去。trigger 时，会依次调用 dep 中存放的 effect。ref 的 track 处理更加简单，dep 是在 `RefImpl` 实例内部维护的，track 时直接将 activeEffect 添加进 dep 即可。

ref 直接使用自身 dep，reactive 则按 `target -> key -> dep` 查找。新增、删除、数组长度变化还会影响遍历等依赖，所以一次操作可能通知多个 dep。

数据变化后，Vue 找到相关 effect。有 scheduler 就交给它调度，没有 scheduler 就执行 `run()`。依赖通知和页面更新之间还隔着调度这一层，后面会接到组件渲染流程。

> WeakMap 对键使用弱引用，WeakSet 对成员使用弱引用，不会阻止对象被 GC 清理。WeakMap 的键被清理后，对应值没有其他引用时也可以回收；具体回收时机由引擎决定。
>
> ```js
> const weakTest = new WeakMap()
> 
> let obj = { text: 'pick a place' }
> 
> weakTest.set(obj, true) // 此时 weakTest 有一个 obj 为 key 的键值对
> 
> console.log(weakTest);
> // 清除原有对象的引用
> // 刚清除引用，不会有变化
> // 等到下一轮 GC 完成，对象被清除后
> // 会发现 weakTest 没有元素了
> // chrome 可以在 performance 手动触发 GC
> obj = null 
> ```

## Effect

前面一直在把 effect 加入 dep，现在看它自己怎么运行。一个 effect 包含两部分：需要执行的函数，以及这次执行建立的依赖关系。Vue 3.2 用 `ReactiveEffect` 保存这些信息。

### 从普通函数到订阅者

把开头的例子改一下：

```js
import { ref, effect, stop } from '@vue/reactivity'

const count = ref(22)
const runner = effect(() => {
  console.log(count.value)
})

// 创建时执行，打印 22
count.value = 33 // 打印 33

stop(runner)
count.value = 44 // 不再自动执行
```

`effect(fn)` 默认先执行一次 fn。Vue 在执行期间把当前实例放进 `activeEffect`，读取 `count.value` 就能找到它，再交给 `trackEffects` 建立订阅。

返回的 `runner` 是绑定到这个实例的 `run` 方法，`runner.effect` 指向实例。`stop(runner)` 移除订阅，后续数据变化不再触发它。我们仍能手动调用 runner；停止后的 runner 会直接执行 fn，不会重新激活自己的订阅。

这里用 `@vue/reactivity` 单独演示底层机制。写组件时，Vue 已经替渲染函数创建了 effect，我们不需要再包一层。

### run 如何管理当前 effect

Vue 3.2 的 `ReactiveEffect` 主要保存 `fn`、`scheduler`、`active`、`deps` 和 `parent`。`deps` 是当前 effect 订阅的 Dep 数组，`parent` 保存嵌套执行前的 effect。

`run()` 的过程可以按下面的顺序读。这是流程示意，具体实现见 [effect.ts](https://github.com/vuejs/core/blob/v3.2.47/packages/reactivity/src/effect.ts)。

```text
已经停止：直接调用 fn，返回结果
检查 parent 链，阻止同一个 effect 重入
保存 activeEffect 和 shouldTrack
将当前实例设为 activeEffect，开启收集
标记旧依赖（嵌套过深时，先清空旧依赖）
try：执行 fn，getter 收集本轮依赖
finally：清理失效依赖，恢复外层 effect 和收集状态
```

需要恢复外层 effect，是因为执行可能嵌套。外层读取数据 A，中间执行一个内层 effect，之后继续读取数据 B。内层结束后，`activeEffect` 必须指回外层，B 才会记录到正确的订阅者上。

清理和恢复放在 `finally` 中。fn 抛出异常也要退出当前收集环境，不能把后续无关的读取算到这个 effect 里。

触发时还会检查 `effect !== activeEffect`。effect 执行过程中修改了自己读取的数据，默认不会因此递归调用自己。这个保护只处理当前执行的重入；两个 effect 相互修改数据，仍可能形成循环。`allowRecurse` 也不是解决循环的通用开关。

### deps 为什么要双向保存

前面的 `trackEffects` 同时做了两件事：

```text
dep.add(activeEffect)         数据记录订阅它的 effect
activeEffect.deps.push(dep)   effect 记录自己订阅的数据
```

只保存第一条关系，就能通知更新，却很难取消订阅。Vue 还需要在分支切换、停止侦听、卸载组件时移除订阅，所以 effect 也保存自己加入过的 dep。

最直接的清理办法，是每次运行前从所有旧 dep 中删除自己，运行时再重新加入。Vue 3.2 对常见情况做了优化：保留仍在使用的订阅，只删除本轮没用到的部分。

前面看到的 `dep.w`、`dep.n` 就用在这里。两者是位标记，不是普通布尔值：`w` 记录运行前已有的依赖，`n` 记录本轮读取的依赖；`trackOpBit` 根据当前嵌套深度选取其中一位。具体处理在 [dep.ts](https://github.com/vuejs/core/blob/v3.2.47/packages/reactivity/src/dep.ts)。

以 `enabled ? text : '关闭'` 为例：

1. 重新执行前，`initDepMarkers` 给 enabled 和 text 对应的 dep 标记 `w`。
2. 执行时只读取 enabled，`trackEffects` 给它标记 `n`。
3. 执行结束，`finalizeDepMarkers` 删除有 `w`、没有 `n` 的 text 订阅，保留 enabled。
4. 清除本层使用的标记位，压缩 effect.deps，留给下次运行。

本轮多次读取同一个属性，`n` 还能避免重复收集。嵌套深度超过 30 时，Vue 3.2 不再使用这套位标记，回退到运行前全部清理、运行时重新收集的方式。

`stop()` 也沿着 effect.deps 清理，但会移除全部订阅，再执行 `onStop` 并标记为不活跃。在自己的执行过程中调用 stop，需要推迟到退出本轮运行时处理，避免正在收集的依赖与清理互相干扰。

### scheduler 决定什么时候执行

数据变化不一定立刻执行 fn。`triggerEffect` 遇到 scheduler，会调用 scheduler，把执行时机交给外部。没有 scheduler，底层 effect 默认同步执行。

下面用一个 Set 收集任务，演示“先通知，稍后统一执行”。它只是演示调度职责，不是 Vue 的任务队列实现。

```js
import { ref, effect } from '@vue/reactivity'

const count = ref(0)
const jobs = new Set()
const runner = effect(() => {
  console.log(count.value)
}, {
  scheduler() {
    jobs.add(runner)
  }
})

count.value = 1
count.value = 2
// 此时只打印过初始化的 0，队列里只有一个 runner

for (const job of jobs) job() // 打印最新值 2
jobs.clear()
```

Vue 的组件更新使用另一层调度器：`queueJob` 去重任务，通过 Promise 微任务安排 `flushJobs`。这也是连续修改数据后，页面通常只更新一次的原因。响应式数据本身已经同步改变，延后的是任务执行。

Vue 3.2 队列还根据组件 uid 排序，让父组件的更新任务先执行。父组件更新可能卸载子组件，已经失效的子组件任务就可以跳过。实现见 [scheduler.ts](https://github.com/vuejs/core/blob/v3.2.47/packages/runtime-core/src/scheduler.ts)。

## computed：缓存与失效通知

computed 既读取其他响应式数据，也供其他 effect 读取。它处在依赖链中间：

```text
count 的 dep → computed 内部的 effect → computed 自己的 dep → 渲染 effect
```

Vue 3.2 的 `ComputedRefImpl` 保存 `_value`、`_dirty` 和一个内部 `ReactiveEffect`。首次读取 `.value` 才运行 getter；结果写进 `_value`，`_dirty` 改成 false。后续读取直接返回缓存。

依赖变化时，内部 effect 的 scheduler 把 `_dirty` 改回 true，再通知订阅 computed 的 effect。它不会在这个 scheduler 中直接计算新值，下一次读取 `.value` 才重新计算。

```js
import { ref, computed } from 'vue'

const count = ref(1)
let calls = 0
const doubled = computed(() => {
  calls++
  return count.value * 2
})

console.log(calls) // 0，还没读取
console.log(doubled.value, calls) // 2, 1
console.log(doubled.value, calls) // 2, 1，使用缓存

count.value = 2
console.log(calls) // 1，只标记失效
console.log(doubled.value, calls) // 4, 2，重新计算
```

读取 computed 时，Vue 先收集外层 effect 对 computed 的依赖，再运行内部 effect 收集 getter 的依赖。两个订阅关系各自保存，不能只把 computed 当成一个普通 getter。

前面 `triggerEffects` 优先通知 computed，就是为了先让缓存失效。普通 effect 同时读取原数据和 computed 时，不能拿到新原数据配上旧缓存。这个顺序也不代表底层 effect 一定只执行一次；组件任务去重还需要 scheduler。

上面讨论的是客户端缓存路径，Vue 3.2 的 SSR 路径另有 `_cacheable` 判断。源码见 [computed.ts](https://github.com/vuejs/core/blob/v3.2.47/packages/reactivity/src/computed.ts)。getter 应只计算并返回结果，网络请求、修改其他状态更适合放进 watch。可写 computed 则把赋值交给用户提供的 setter，缓存仍由 getter 的依赖决定。

## watch 和 watchEffect：把依赖连接到回调

computed 用依赖产生一个值，watch 用依赖触发回调。Vue 3.2 的入口在 [apiWatch.ts](https://github.com/vuejs/core/blob/v3.2.47/packages/runtime-core/src/apiWatch.ts)，核心是 `doWatch`。

### watch 的 getter 和 job

watch 先把 source 转成 getter：ref 读取 `.value`，函数直接作为 getter，多来源数组逐项取值。传入 reactive 对象时，默认还会深度遍历。

然后创建 `ReactiveEffect(getter, scheduler)`。默认先运行 getter，建立订阅并保存 oldValue，不执行回调。`immediate: true` 则立即执行一次包含回调的 job。

```text
source 变化
→ scheduler 安排 job
→ job 调用 effect.run()，得到 newValue 并更新依赖
→ 检查变化（deep、forceTrigger 等情况另作处理）
→ 清理上一轮副作用，调用 callback(newValue, oldValue, onCleanup)
→ 保存 newValue，供下一轮比较
```

watch 收集的是 source getter 读取的依赖，回调里额外读取的数据不会成为这个 watcher 的来源：

```js
import { ref, watch } from 'vue'

const count = ref(0)
const label = ref('次数')

watch(count, (value) => {
  console.log(label.value, value)
})

label.value = '总数' // 不触发这个 watch
count.value++ // 触发，回调读取最新的 label
```

`watchEffect` 则直接把用户函数作为收集入口，默认立即运行，自动订阅它读取的数据。函数里有 await 时，只收集同步执行阶段的读取；await 之后已经离开当前收集环境，后面的读取不会自动加入依赖。用异步函数时，我更愿意在 await 前把需要追踪的数据取出来。

### deep 为什么能监听嵌套修改

`deep` 的核心是 `traverse`，它在 effect 运行期间递归读取对象属性。这些读取经过 Proxy getter，逐个建立订阅。它并没有为 watch 再创建一套代理，也不会保存整份对象的历史快照。

```js
import { reactive, watch } from 'vue'

const state = reactive({ user: { name: 'Welkin' } })

watch(() => state.user, () => {
  console.log('user 被替换')
})

watch(() => state.user, (newValue, oldValue) => {
  console.log(newValue === oldValue)
}, { deep: true })

state.user.name = 'Zhou' // 只有 deep watcher 响应，打印 true
```

getter 返回对象，默认只监听它返回的对象是否被替换。直接 `watch(state, callback)` 则默认深度监听。嵌套属性修改时，新旧值仍指向同一个对象，不能拿 oldValue 当修改前的快照。需要历史对比，应自行保存快照，或只侦听需要比较的属性。

### flush 与 DOM 更新时机

watch 和 watchEffect 默认使用 `flush: 'pre'`。任务经过批处理，在所属组件 DOM 更新前执行；默认回调里读取这个组件的 DOM，可能还是旧结果。

- `pre`：默认值，组件更新前执行，适合大多数状态处理。
- `post`：组件 DOM 更新后执行，适合读取更新后的元素。
- `sync`：数据触发时同步执行，不经过异步队列批处理，连续修改会连续触发。

这些选项决定的是更新时的调度。首次执行还要结合 API 看：普通 watch 默认只收集来源，immediate watch 会立即调用回调；watchEffect 默认立即运行，post watchEffect 的首次运行会排到渲染后。

官方文档对回调时机和首次执行有完整说明，见 [侦听器](https://cn.vuejs.org/guide/essentials/watchers)。

### 清理上一轮副作用

依赖清理只负责取消订阅，不会替我们取消网络请求。快速切换 id 时，上一次请求可能晚回来，覆盖新结果。watch 提供的 onCleanup 用来处理这类资源。

```js
import { ref, watch } from 'vue'

const id = ref(1)
const result = ref(null)

const stopWatch = watch(id, async (value, _oldValue, onCleanup) => {
  const controller = new AbortController()
  onCleanup(() => controller.abort())

  try {
    const response = await fetch(`/api/items/${value}`, {
      signal: controller.signal
    })
    const data = await response.json()
    if (!controller.signal.aborted) result.value = data
  } catch (error) {
    if (error.name !== 'AbortError') throw error
  }
}, { immediate: true })

// 不再需要时调用 stopWatch()，也会执行已注册的清理
```

下一次回调执行前，Vue 调用上一轮的清理函数；停止 watcher 时也会调用。这里的资源清理，与前面移除过期 dep 的清理是两件事。

Vue 3.5 还提供 `onWatcherCleanup`，需要在 watcher 同步执行阶段注册，不能等到 await 之后再调用。上例使用回调参数 onCleanup，能兼容本文前面的 Vue 3.2 分析。

## 组件更新如何接上响应式

[挂载流程](./03-mount.md) 中的 `setupRenderEffect` 创建了组件的 ReactiveEffect。它的 fn 是 `componentUpdateFn`，scheduler 把 `instance.update` 交给 `queueJob`。

第一次调用 update，会运行渲染函数并挂载 DOM。模板中读取的响应式数据在这次执行里订阅渲染 effect。后续数据改变，流程就接起来了：

```text
修改 ref.value 或 reactive 属性
→ 找到关联 dep，通知渲染 effect
→ scheduler 将组件更新任务加入队列
→ 微任务执行 update，再次运行 componentUpdateFn
→ renderComponentRoot 生成新 VNode，同时更新依赖
→ patch 比较新旧 VNode，更新 DOM
```

响应式系统负责找出谁需要更新，渲染器负责更新 DOM。两者通过组件的 effect 和 scheduler 连接。

```js
import { ref, nextTick } from 'vue'

// 放在 setup 中，模板已经使用 count
const count = ref(0)

async function increment() {
  count.value++
  console.log(count.value) // 新值已可读取
  await nextTick()
  // 本轮组件更新完成，可以读取更新后的 DOM
}
```

`nextTick` 等待当前更新队列完成，没有待执行任务时使用已完成的 Promise。它不会主动制造一次渲染，也不保证浏览器已经完成绘制。

### effectScope 与卸载

每个 effect 单独 stop 还不够，组件里可能同时创建多个 watch、watchEffect。Vue 用 effectScope 收集一组 effect，再统一停止。Vue 3.2 的 ReactiveEffect 构造时会通过 `recordEffectScope` 加入当前作用域，组件也有自己的 `instance.scope`。

```js
import { effectScope, ref, watchEffect, onScopeDispose } from 'vue'

const count = ref(0)
const scope = effectScope()

scope.run(() => {
  watchEffect(() => console.log(count.value))
  const timer = setInterval(() => count.value++, 1000)
  onScopeDispose(() => clearInterval(timer))
})

scope.stop() // 停止 watcher，同时清理计时器
```

在 setup 中同步创建的侦听器会跟随组件卸载停止。异步回调里新建的侦听器不会自动归入原组件作用域，需要自己保存停止函数并清理。计时器等外部资源也要注册清理函数，scope 不会自动识别它们。源码和 API 分别见 [effectScope.ts](https://github.com/vuejs/core/blob/v3.2.47/packages/reactivity/src/effectScope.ts)、[effectScope 文档](https://cn.vuejs.org/api/reactivity-advanced#effectscope)。

## Vue 3.5 的实现变化

上面这套 `Dep = Set + w/n`、`activeEffect` 和 computed 内部 ReactiveEffect 的描述，对应 Vue 3.2。当前稳定版 3.5.43 保留了读取建立订阅、修改通知订阅者的基本流程，但换了依赖的存储和更新方式。

### Dep、Link 和版本号

在 Vue 3.5 中，Dep 是一个类。它通过 Link 连接订阅者；Link 同时挂在订阅者的依赖链和 Dep 的订阅链上，可以从两侧移除。`targetMap` 仍按原对象、属性找到 Dep，ref 则持有自己的 Dep。

新实现用 `activeSub` 表示当前订阅者。重新运行前，把旧 Link 的 version 标记为 -1；本轮读取会复用 Link 并同步版本，运行后删除仍为 -1 的 Link。这里已经没有 Vue 3.2 的 `w/n` 位标记，也没有超过 30 层就回退的那套分支。依赖结构见 [3.5.43 dep.ts](https://github.com/vuejs/core/blob/v3.5.43/packages/reactivity/src/dep.ts)。

Dep 的 version 记录自身变化，Link 的 version 记录订阅者上次确认的版本。Vue 可以据此判断依赖是否变化，减少不必要的执行。运行与清理的细节见 [3.5.43 effect.ts](https://github.com/vuejs/core/blob/v3.5.43/packages/reactivity/src/effect.ts)。

### computed 不再额外创建 ReactiveEffect

Vue 3.5 的 ComputedRefImpl 自己就是订阅者，直接维护依赖链、标记和缓存。读取 `.value` 时调用 `refreshComputed`，结合全局版本与依赖版本判断是否需要重新计算。源码中的 `effect` 属性只是兼容用途，指向 computed 自身。

计算结果变化时，computed 才推进自身 Dep 的版本；下游 effect 检查依赖后，能跳过计算结果未变的更新。下面这个行为从 Vue 3.4 开始就已提供，不适合拿来解释 Vue 3.2 的 `_dirty` 实现：

```js
import { ref, computed, watchEffect, nextTick } from 'vue'

const count = ref(0)
const isEven = computed(() => count.value % 2 === 0)

watchEffect(() => console.log(isEven.value)) // true

count.value = 2
await nextTick()
// computed 的结果仍是 true，watchEffect 不再执行
```

getter 每次返回新对象时，对象引用仍会变化，不能自动得到相同的跳过效果。实现见 [3.5.43 computed.ts](https://github.com/vuejs/core/blob/v3.5.43/packages/reactivity/src/computed.ts)，行为说明见 [计算属性稳定性](https://vuejs.org/guide/best-practices/performance#computed-stability)。

### 响应式批处理与组件队列

Vue 3.5 的响应式层用 `startBatch`、`endBatch` 合并一轮通知，避免通知链中重复处理订阅者。这层批处理在最外层 batch 结束时处理待触发的 effect，本身不会安排 Promise 微任务。

组件的 scheduler 仍会把更新交给 runtime-core 的队列。读取源码时，要区分响应式层的一轮通知与组件层的异步更新：底层 effect 没有 scheduler，默认仍同步执行。

watch 的基础实现也已移到 [reactivity/watch.ts](https://github.com/vuejs/core/blob/v3.5.43/packages/reactivity/src/watch.ts)，[runtime-core/apiWatch.ts](https://github.com/vuejs/core/blob/v3.5.43/packages/runtime-core/src/apiWatch.ts) 再接入组件实例、错误处理和调度时机。Vue 3.5 的 deep 支持数字深度，watch 停止句柄还带有 pause、resume；这些接口需要按对应版本阅读。

回头看这条链路，getter 的职责是建立订阅，setter 的职责是通知变化，effect 管理执行和依赖，scheduler 安排时机。computed、watch 和组件渲染分别在这条链上增加缓存、回调和 DOM 更新。内部结构会随版本变化，这几个职责仍能帮助我们找到源码入口。
