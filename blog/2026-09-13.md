[审核发布流程](./2026-09-07.md)加上后，我继续处理解析质量。MinerU 生成的 Markdown 可能保留目录、压平标题层级，或把代码行误认成标题；这些格式问题会沿着切片进入检索。

## 结构检查

假设 MinerU 把“安装步骤”压成普通段落，又把目录里的锚点链接留在正文里。解析审核页需要先把这类格式风险指出来，方便编辑者对照原文检查。我加了一次“粗审核”：检查 ATX 标题层级、重复标题、编号跳跃、目录残留、失效锚点和疑似未围栏代码。它是本地规则，不调用 LLM，也不自动批准文档。规则能确定的换行或 Setext 标题才生成保守修订草稿；章节归属和缺失内容交给人判断。

粗审返回问题代码、行号、提示和是否自动修订；结果仍是待人检查的草稿。例如行号对应输入文本，自动修订只标记确定的格式转换：

```python
ReviewIssue(
    code="setext_heading",
    line=12,
    severity="info",
    message="Setext 标题不被入库建树识别",
    suggestion="转换为 ATX 标题",
    auto_fixed=True,
)
```

这类问题列表能定位格式，不判断内容是否正确，也不替人补写缺失段落。标题层级、章节归属需要结合原始文档判断。

规则扫描会先识别代码围栏，围栏内部不按标题解析；遇到正文标题时，再比较当前层级与前一个标题。下面是对应逻辑的简化伪代码，省略编号、锚点等其他规则：

```text
for line in markdown:
    if line opens or closes a code fence:
        update fence state
        continue
    if inside code fence:
        continue
    if line is an ATX heading:
        level = count leading '#'
        if level > previous_heading_level + 1:
            report("heading_jump", line_number)
        previous_heading_level = level
```

目录另作处理。独立的 `[TOC]`、`[[TOC]]`，或标题为“目录”等且列表项全部指向本文锚点的章节，会标记为 TOC 块。生成父子块时排除它，避免目录里的标题链接反复命中。若列表混有普通内容，仍按正文处理，不能只看到“目录”两个字就删。

目录识别也需要同时满足标记或标题上下文与列表内容条件：

```text
if block is standalone [TOC] or [[TOC]]:
    classify as TOC
elif parent_heading names a table of contents and every non-empty list item links to #anchor:
    classify as TOC
else:
    keep as ordinary content
```

解析后再切片，排除目录的动作在切片单元生成时完成。关键条件很小：

```python
for block in section.blocks:
    if block.type == BlockType.TOC:
        continue
    text = block.content.strip()
    if text:
        units.append((text, block.type in _ATOMIC_TYPES))
```

`TOC` 仍留在解析树里供审核，不进入检索块。表格、代码、公式和图片则标为原子单元，切片时尽量整块保留。这里不能把所有列表都当目录，否则正常的步骤说明会丢失。

## 版本修订

人工保存会生成新的 ParseVersion，记录它基于哪一版。重新调用 MinerU 则得到新的原始解析版本。这样审核时能回看解析原件，也能追踪哪次修改引入了问题。未保存修改时不能直接通过、拒绝或重解析，避免页面上的内容与真正入库的版本不一致。

例如解析把“安装步骤”误识别成普通段落，我会在审核页改成正确标题并保存为下一版，再检查这版生成的 Section 和子块。直接覆盖 MinerU 输出虽然省一步，却会失去对照，后面很难判断是解析错误还是人工修订造成的。

粗审输出只是问题清单和候选文本，最终仍要人工确认。文本结构还原得再完整，也需要进入[索引代发布](./2026-09-07.md)后才会影响线上检索。
