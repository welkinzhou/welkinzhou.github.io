[多 Agent 图](./2026-09-19.md)让 Knowledge 子图按需要检索。设想同一位员工能访问两个知识库，但本轮问题只发现了其中一个；模型生成的另一个库 ID 不能直接变成数据库访问。检索工具需要把选择放回当前登录身份、租户和本轮允许的资源范围中检查。

## 发现与检索

未绑定知识库时，Knowledge 子图先用名称或描述发现当前租户内的候选库，再把发现得到的 ID 传给搜索工具。发现为空就返回 `no_evidence`，不猜一个库继续查。执行正文检索时，还会核对 `chat:use`、`kb:read` 和具体资源范围。权限分两层：策略先判断当前身份能否调用 Knowledge 工具，执行器再核对知识库 ID 是否属于本轮允许范围，并按租户读取资源。工具目录规定各专业 Agent 能用什么，模型输出不能修改工具权限或最大调用次数。

权限判断先限定登录身份和专业 Agent，再由具体工具校验知识库范围。工具只有在策略允许时才进入执行；Knowledge 工具还要把已发现的库和会话绑定库合成当前允许集合，再用租户条件读取资源。关键步骤的伪代码如下：

```python
if not policy.allows(actor, definition):
    return denied()

allowed_kb_ids = set(discovered_kb_ids)
if bound_kb_id is not None:
    allowed_kb_ids.add(bound_kb_id)
if selected_kb_id not in allowed_kb_ids:
    return permission_denied()

kb = await knowledge_base_repo.get_by_id(
    selected_kb_id, tenant_id=actor.tenant_id
)
if kb is None:
    return permission_denied()
```

这段是按源码关系整理的伪代码。`policy.allows` 检查 `chat:use` 和专业 Agent 对应权限；执行器随后校验知识库是否在本轮允许集合中，并确认资源属于当前租户。比如模型提供一个本轮未发现、也未绑定的 `knowledge_base_id`，就会在检索前被拒绝。

检索结果也要保留来源。子块在 Milvus 和 ES 里召回，融合、重排后按父块 ID 展开，让回答能看到比命中片段更完整的上下文；去重仍保留排序。若只给模型一个脱离章节的小片段，它可能把局部说法扩展成整篇文档的结论。

检索服务在两路结果之后用带 `chunk_id` 的 RRF 融合，再重排并展开父块。若两路都失败会报错；若一路失败，会留下失败通道信息。这个区别进入评测尤为重要：BM25 因 IK 词典出错时，剩下的向量结果即使能回答几题，也不能拿这轮分数评价标题权重。

## 结果状态

外部服务没配置、超时、权限不足和确实没有找到资料是不同状态。工具返回的“没有证据”是正常完成但结果为空，例如：

```json
{"ok":true,"status":"no_evidence","items":[]}
```

知识库发现工具会同时返回 `ok: true`；外部能力未配置或工具执行失败则以 `ok: false` 和错误状态返回，例如：

```json
{"ok":false,"status":"error","error":"知识库发现能力未配置"}
```

检索通道若有一路失败，也要留下 `failed_channels`；评测时 BM25/IK 出错更不能把分数当成可信的优化结果。

这是我从固定 RAG 走向工具化 RAG 后补的一层约束：Agent 可以决定何时查资料，是否有权查、查到了什么、答案能不能由这些内容支持，仍要由程序和证据来确定。
