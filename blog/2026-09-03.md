## Golden Set

评测要有固定的问题、参考答案和原文出处。`question` 记录问题，`reference` 提供判断依据，`source_chunk_ids` 让人回到原文核对参考答案。

当前代码把整批题和单条问答分成 `GoldenSet`、`GoldenSample` 两个值对象。下面保留了实际参与评测的字段；数据库另外记录创建人、生成状态和审核状态。

```python
from dataclasses import dataclass
from enum import StrEnum
from uuid import UUID


class GoldenSource(StrEnum):
    SYNTHETIC = "synthetic"
    FEEDBACK = "feedback"
    MANUAL = "manual"


@dataclass(slots=True, frozen=True)
class GoldenSample:
    sample_id: str
    question: str
    reference: str
    source: GoldenSource
    kb_id: UUID | None = None
    tenant_id: UUID | None = None
    source_chunk_ids: tuple[str, ...] = ()
    tags: tuple[str, ...] = ()
    index_generation_id: UUID | None = None


@dataclass(slots=True, frozen=True)
class GoldenSet:
    name: str
    version: str
    samples: tuple[GoldenSample, ...]
    index_generation_ids: tuple[UUID, ...] = ()
```

`question` 和 `reference` 是最基本的题目与参考答案。反向 QA 可以从父块生成候选，点踩反馈可以导入草稿，也允许人工修改；只有经过审核的内容才用于正式评测。`source_chunk_ids` 记录答案依据的父块或片段，审核时可以回看原文。题目、答案和出处放在一起，才能检查这道题本身是否可靠。

复用这批题时，还得知道它依据的是哪一版资料。单题的 `index_generation_id` 记录来源索引代，`kb_id`、`tenant_id` 限定所属知识库和租户。整批题的 `index_generation_ids` 在创建时从已发布索引代取得快照，后来重建文档，也能查出旧题当初依据哪一代资料。`name` 是显示名，`version` 当前用 `v1` 标记这一批次，不是文档解析版本；`samples` 保存题目，正式评测时服务层只取审核通过的样本。

另外几个字段容易被忽略，却能帮我解释结果。`sample_id` 是批次内的业务 ID，用来把预测、逐题分数和原题对齐；反向出题的样本以来源父块 ID 生成，数据库另有自己的 UUID 主键。`source` 区分反向生成、反馈和人工录入，`tags` 记录题型等生成信息。分数异常时，可以沿着来源回查原文，也能看是否只有某类题集中退化，而不是只盯着一个均分。

## 从父块生成并审核

后台创建 Golden Set 时提交知识库、期望题数和名称。这个请求只负责入队，生成任务会从该库已发布的父块抽取候选。`count` 是期望数，不保证每个候选都能通过证据检查。以下是接口的最小用法，`TOKEN`、`KB_ID` 和返回的 `SET_ID` 换成自己环境里的值：

```bash
curl -X POST 'http://localhost:8000/api/v1/eval/golden-sets' \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d "{\"kb_id\":\"$KB_ID\",\"count\":20,\"name\":\"检索基线\"}"
```

创建和审核要求 `eval:admin` 权限。候选题生成后，在管理端逐条或按批审核；没有待审核题且至少一题通过，才能启动评测。自动生成的参考答案可能看似完整，却夹带原文没有的判断，所以这里保留人工核对。

## 评测指标

评测先用 `question` 检索并生成 `answer`，得到 `retrieved_contexts`，再把这三个字段和 `reference` 交给 RAGAS。适配器构造的数据行就是下面这样：

```python
row = {
    "user_input": prediction.question,
    "retrieved_contexts": list(prediction.retrieved_contexts),
    "response": prediction.answer,
    "reference": prediction.reference,
}
```

RAGAS 返回的原始值是小数，四项都是越高越好，但读法不同。Context Recall 和 Faithfulness 是比例，可以换算成百分比；Context Precision 和 Answer Relevancy 是分数，不能按“答对了百分之几”理解：

- **[Context Precision](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/context_precision/)**：`0～1` 的排序分数。有用的片段排得越靠前，分数越高。`0.8` 不表示 80% 的召回片段有用，片段顺序也参与计算。
- **[Context Recall](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/context_recall/)**：`0～1` 的覆盖比例。参考答案拆出 4 个断言，召回内容支持其中 3 个时，得分 `0.75`，可读作 75% 的参考答案断言得到覆盖。
- **[Faithfulness](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/faithfulness/)**：`0～1` 的支持比例。生成答案拆出 4 个断言，其中 3 个能由召回内容支持时，得分 `0.75`，可读作 75% 的回答断言有依据。
- **[Answer Relevancy](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/answer_relevance/)**：回答与问题的相似度分数。RAGAS 根据回答反推问题，再与原问题比较；通常落在 `0～1`，理论上可能为负。`0.8` 是相似度得分，不表示事实有 80% 正确。

前两项主要定位检索问题，后两项主要检查生成答案。

审核完成后，管理端可以异步启动评测；没有界面时也能用 CLI 跑同一个已审核的 Set，并输出逐题报告：

```bash
cd backend
uv sync --extra dev --extra eval
uv run python -m app.eval run \
  --tenant-id "$TENANT_ID" \
  --set-id "$SET_ID" \
  --out report.md
```

结果写入 PostgreSQL，页面可以比较历史曲线，`report.md` 还能看逐题预测与分数。均分是逐题分数的平均，`0.8` 不代表 80% 的题答对了。调切片或标题权重时，我会先固定题集、发布代、生成模型和裁判模型，再看分数变化；否则看到一个更高的均分，也不知道是哪一处条件改变了。
