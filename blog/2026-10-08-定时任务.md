[工具确认](./2026-09-05.md)最初处理的是一封邮件。设想用户希望每周一早上收到知识库评测提醒：助手要把时间、时区和提醒内容整理成计划，再请用户确认。用户确认后，这份计划会在未来持续执行，因此确认表达的是对后续执行的授权，不只是对当前这条消息的认可。

<!-- truncate -->

## 计划确认

Action 子图整理任务名称、动作、时间或 cron、时区、结束时间、迟到容忍窗口、渠道和消息内容，再展示确认卡。缺字段时先让用户填写；编辑后重新校验下一次执行时间。身份和租户由服务端写入，模型不能自行指定。创建与修改需要确认；停止和查看运行记录走各自工具权限。

确认的计划使用 `ScheduledTaskSpec` 校验。前面的场景是每周一早上提醒，下面用上海时间每周一 9 点表示；项目 cron 规则按“分 时 日 月 星期”填写：

```json
{
  "title": "检查知识库评测",
  "body": "查看新索引代的评测结果",
  "action": "reminder",
  "channels": "in_app",
  "schedule_type": "cron",
  "cron": "0 9 * * 1",
  "timezone": "Asia/Shanghai"
}
```

这是计划内容示例，不是可直接绕过确认调用的接口。选择 `once` 必须给带时区的 `run_at`、不能同时给 `cron`；选择 `cron` 则必须提供规则且不能给 `run_at`。邮件渠道还需要收件人。确认卡会展示这些字段及下次执行时间，用户修改后再校验，避免批准的是旧计划、实际保存的是另一份参数。服务端只在确认后保存计划，并自行补上用户、租户和当前授权版本，模型不能提供这些身份字段。

确认卡必须说清楚这是持续授权，不是只批准下一次执行。存储时，`scheduled_tasks` 保存当前计划、`status`、授权 `version` 和 `next_run_at`；每次触发另建一条 `scheduled_task_runs`，保存当时的版本与计划快照。任务可以发邮件、站内提醒或两者一起；邮件服务配置为日志模式时，该次投递只能记为模拟结果，不能告诉用户邮件已送达。这样才能追查计划仍为 `active`、但某次运行已是 `missed` 或 `failed` 的情况。

## 执行记录

Beat 扫描到期任务并生成运行记录。错过容忍时间会记为 `missed`，已有未完成运行则记为 `skipped`，不会无限补发；周期任务离线期间错过的多个时点也不会逐条补发。运行之后，各渠道有自己的投递状态，例如 `pending`、`sent`、`simulated`、`uncertain` 或 `failed`。邮件发送放在数据库事务外，站内提醒显示在顶栏。用户在聊天里听到“已设置”之前，服务端必须确认计划写入成功；之后是否真正送达，还要看运行记录和渠道结果。

一次触发要先决定是否应创建待投递运行，再逐渠道领取。下面省略锁、恢复和字段赋值，展示状态转移及邮件副作用的边界：

```python
if lateness_seconds > spec.grace_seconds:
    run.status = "missed"
elif has_unfinished_run(task.id):
    run.status = "skipped"
else:
    run.status = "pending"
    create_channel_deliveries(status="pending")

dispatch = transactionally_claim_email_delivery()
if dispatch is None:  # 没有可领取的邮件投递，不执行发送
    return
# 领取事务提交后，delivery/run 状态为 sending
try:
    await sender.send_email(dispatch.to, dispatch.subject, dispatch.body)
except Exception:
    save_delivery_status("uncertain")  # SMTP 可能已接收，不能盲目重试
else:
    save_delivery_status("simulated" if provider == "log" else "sent")
```

实际领取时还会重查任务是否仍为 `active`、任务版本是否与运行快照一致，以及用户权限是否有效。邮件发送发生在数据库事务之外；发送前先持久化 `sending`，发送结果再单独落库。服务异常时记为 `uncertain`，因为 SMTP 可能已经接收邮件，自动重试会造成重复发送。

这一步把助手从查询资料推进到可执行任务，也把[多 Agent 图](./2026-09-19.md)里的确认、权限、预算与真实副作用串起来了。当前 RAG 与助手主线的文章写到这次提交为止。
