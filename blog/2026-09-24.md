[索引代发布](./2026-09-07.md)的规则写在代码里后，还要确认检索只看当前发布的索引代。即使 ES 或 Milvus 里残留了旧数据，只要发布指针已切换，用户也不应搜到旧代内容。假的 Repository 很难发现真实字段映射、过滤表达式或事务提交的问题，因此我用隔离容器检查实际服务。

## 两路检索

检索先由 PostgreSQL 按租户、知识库、文档状态和当前索引代状态找出可见的发布代；没有可见代时直接返回空。然后 ES 的 BM25 与 Milvus 向量查询都带上租户、知识库和这组发布代过滤。集成测试写入同一索引代的子块和固定向量，检查发布前不可见、发布后两路可见、错租户或空发布代不可见，以及下架后再次不可见。重复写入相同的确定性 chunk ID，也不会新增一份记录。

PostgreSQL 的当前指针决定本次查询允许使用哪些发布代，两路检索收到相同的租户、知识库和代 ID 范围。下面是实际检索顺序的伪代码，省去 channel 和异常处理细节：

```python
generation_ids = await document_repo.list_published_generation_ids(
    kb_id, tenant_id=tenant_id
)
if not generation_ids:
    return empty_result()

scope = {
    "tenant_id": tenant_id,
    "kb_id": kb_id,
    "published_generation_ids": generation_ids,
    "top_k": 20,
}
bm25_hits = await es_repo.search_bm25(query, **scope)
vector_hits = await milvus_repo.search(query_vector, **scope)
```

ES 和 Milvus 各自还会检查 chunk 的发布标记，并同时过滤 tenant、knowledge base 和 `index_generation_id`。集成测试的核心断言也围绕同一份 `scope`；下面省去容器、索引和 work item 初始化，只保留发布、拒绝和下架检查：

```python
assert await es_repo.search_bm25("差旅报销", **scope) == []
assert await vector_repo.search(vector, **scope) == []

await executor.execute(publish_work)

assert [hit.chunk_id for hit in await es_repo.search_bm25("差旅报销", **scope)] == [chunk.chunk_id]
assert [hit.chunk_id for hit in await vector_repo.search(vector, **scope)] == [chunk.chunk_id]

for denied in (
    {**scope, "tenant_id": uuid4()},
    {**scope, "kb_id": uuid4()},
    {**scope, "published_generation_ids": []},
):
    assert await es_repo.search_bm25("差旅报销", **denied) == []
    assert await vector_repo.search(vector, **denied) == []

await executor.execute(archive_work)
assert await es_repo.search_bm25("差旅报销", **scope) == []
assert await vector_repo.search(vector, **scope) == []
```

测试中的 `scope` 同时带租户、知识库和发布代；分别改错租户、知识库或清空发布代后，ES 与 Milvus 都应返回空。生产检索还会以 PostgreSQL 当前指针决定允许查询的 generation IDs，因此过期代即使仍留在索引里，也不属于可见范围。这个例子验证的是“同一代是否按预期可见”，不是拿固定向量证明语义检索准确。

PostgreSQL 测试从空库跑生产迁移，再跨事务检查源文件审核、提交与回滚、发布代指针和下架。Redis、RabbitMQ、MinIO 也分别验证了 run 领取与重放、持久消息重投、版本文件的读写和隔离删除。这些测试全部放在临时容器及独立资源里，不碰业务数据。

## 验证边界

这次 ES/Milvus 测试用了固定中文内容和 8 维固定向量，确认的是存储、过滤和发布可见性；PostgreSQL 仓储集成测试另外检查发布指针、事务边界和下架后的空可见集合。它没有验证真实 Embedding 的语义效果，也没有跑融合、重排和模型回答。上传后经 MinerU、审核、Celery 构建直到最终问答的整条链路，当时仍未完成真实验收。

我之前容易把“单个环节通过”当成“链路可用”。现在至少能明确：若刚发布就搜到旧代，先查发布指针和两端标记；若可见性正确但答错，再回到切片、召回和生成质量。
