上一篇确定了文档结构，这次设计入库的表和关联。我把文档、解析版本和索引批次分开管理。

<!-- truncate -->

结构说明见[上一篇](./2026-08-19.md)，这里补审核和发布流程。

实际开发遇到了标题层级错误、格式混乱、标题混入搜索内容等问题。我加了审核和编辑，不再上传后直接切片。

先保存文件，审核通过后解析。检查并编辑解析结果，再生成切片。父块存 PG，子块存 ES 和 Milvus。

## 数据结构

### Document

Document 汇总原文件、解析地址、审核情况和解析状态，不直接存正文。

```bash
Document
├── id
├── tenant_id # 租户归属
├── knowledge_base_id
├── filename
├── source_object_key        # 审核拒绝并删除原文件后置 null
├── content_hash             # 同上，置 null，不参与去重
├── created_by / created_at
├── current_parse_version_id # 当前正在处理、待审或刚被拒绝的解析版本
├── published_parse_version_id # 当前真正供检索使用的解析版本
├── status                   # unpublished / published / rejected / archived
├── rejected_by              # 仅 status = rejected 时有意义
├── rejected_at
└── rejection_reason
```

我分了五种状态：Draft 等待审核，Reject 审核未通过，Unpublished 等待解析入库，Published 按发布版本检索，Archived 下架并保留引用。

状态之间有几个约定：

- `status = published`：`published_parse_version_id` 非空，检索永远只用它。
- 重新解析产生 `parse-v3` 后，`current_parse_version_id = parse-v3`，但仍保持 `published_parse_version_id = parse-v2`、`status = published`。
- `parse-v3` 审核失败：删除 `parse-v3` 的解析产物和索引，`parse-v2` 继续服务，Document 仍是 `published`。
- 首次解析版本审核失败：删除原文件和全部产物，清空 `source_object_key`、`content_hash`，Document 变为 `rejected`，填写 `rejected_*`。
- 被拒文件再次上传：直接新建 `Document`，不做 hash 拦截。

先创建 Document，再按 id 保存文件：

```bash
documents/{document_id}/source/original.pdf
```

### ParseVersion

审核通过后解析，产物按版本保存在 MinIO：

```bash
ParseVersion
├── id
├── document_id
├── version_no # 同一个 Document 下递增，例如 v1、v2、v3。
├── based_on_version_id # 人工修改时记录从哪一版复制而来。
├── status # pending -> parsing -> chunking -> embedding -> ready, failed, purged
├── markdown_object_key # 该版本对应的 Markdown 文件
├── asset_prefix # 该版本解析图片的目录。
├── content_hash # 解析结果内容哈希。
├── parser_name # 解释器名称，可能有多个解析器
├── parser_model # 模型
├── parser_config # 配置
├── created_by
├── created_at
├── submitted_by
├── submitted_at
├── approved_by
├── approved_at
└── rejection_reason
```

status 记录解析进度，包括 failed 和 purged。`based_on_version_id` 标记修改依据，编辑后生成新的 ParseVersion，重新审核。已有版本不覆盖，初始 v0 保留作兜底。

文件目录：

```bash
documents/{document_id}/parses/{parse_version_no}/parsed.md
documents/{document_id}/parses/{parse_version_no}/assets/...
```

### IndexGeneration

同一份解析结果，可以换模型或调整切片大小，生成不同批次。IndexGeneration 关联每次切片的配置和结果。

```bash
IndexGeneration
├── id
├── document_id
├── parse_version_id
├── status
├── chunking_config # 切片配置
├── embedding_model # embedding 模型
├── child_count
├── created_at
└── published_at
```

切片完成后更新父级记录和子块索引状态，让检索找到已发布内容。

这几层分开后，解析修改和索引重建就不用混在一起处理了。
