上一章确定了结构，这一章处理如何入库。包括表和表的关系，怎么关联数据，应该怎么入库。检索和存储应该是两部份，存储信息是为了补全上下文，检索是为了精确定位，是两部份功能。

<!-- truncate -->

父子块是为了检索准确，对话内容充足。检索清晰，需要内容干净。对话内容充足，需要上下文清楚。内容干净，需要对文档做处理，增加审核环节。不合规数据，结构混乱数据不能直接进入知识库。我们通过结构化存储，可以清楚的补全上下文，这一步应该在生成做。

上一节是基础逻辑，实际开发后遇到很多问题。比如文档格式逻辑错乱，层级不对，标题区域也被加进搜索区域。这样文档入库后，就需要增加审核和编辑功能。现在的简单流程如下，文件上传后落盘，审核人员需要判断文档是否合规，违规文档直接删除，不必走解析流程。合规审核通过后，开始走解析流程。解析完成，审核人员对解析结果进行审核和编辑，确保文档解析规范。这一步通过后，才会走切片流程。切片同样是父子块，父块存储进 pg 用作对话语素，子块分别存进 ES 和 Milvus，用于稀疏、稠密召回。

## 数据结构

### Document

从顶层开始设计，首先是 Document。Document 不是简单的文件，他至少需要包含一下信息，原文件、解析文件地址，审核情况，解析状况。他不需要管理具体内容，而是知识库中的一个逻辑概念，负责资源聚合。

```bash
Document
├── id
├── tenant_id # 租户归属
├── knowledge_base_id
├── filename
├── source_object_key        # 审核拒绝并删除原文件后置 null
├── content_hash             # 同上，置 null，不参与去重
├── created_by / created_at
├── current_parse_version_id # 当前正在处理、待审或刚被拒绝的解析版本
├── published_parse_version_id # 当前真正供检索使用的解析版本
├── status                   # unpublished / published / rejected / archived
├── rejected_by              # 仅 status = rejected 时有意义
├── rejected_at
└── rejection_reason
```

文档状态只会有五种：Draft（草稿，刚提交等待违规审核），Reject（审核没通过），Unpublished（待发布，审核通过等待解析入库），Published（已发布，可用状态，根据发布版本检索），Archived（手动下架，不能检索，可以看到引用信息）。

关键语义：

- `status = published`：`published_parse_version_id` 非空，检索永远只用它。
- 重新解析产生 `parse-v3` 后，`current_parse_version_id = parse-v3`，但仍保持 `published_parse_version_id = parse-v2`、`status = published`。
- `parse-v3` 审核失败：删除 `parse-v3` 的解析产物和索引，`parse-v2` 继续服务，Document 仍是 `published`。
- 首次解析版本审核失败：删除原文件和全部产物，清空 `source_object_key`、`content_hash`，Document 变为 `rejected`，填写 `rejected_*`。
- 被拒文件再次上传：直接新建 `Document`，不做 hash 拦截。

Document 创建早于落盘，MinIO 文件地址和 Document id 做关联，例如：

```bash
documents/{document_id}/source/original.pdf
```



### ParseVersion

文档审核通过后，开始走解析流程。解析后会生成文件，根据解析版本，在 MinIO 落盘。

```bash
ParseVersion
├── id
├── document_id
├── version_no # 同一个 Document 下递增，例如 v1、v2、v3。
├── based_on_version_id # 人工修改时记录从哪一版复制而来。
├── status # pending -> parsing -> chunking -> embedding -> ready, failed, purged
├── markdown_object_key # 该版本对应的 Markdown 文件
├── asset_prefix # 该版本解析图片的目录。
├── content_hash # 解析结果内容哈希。
├── parser_name # 解释器名称，可能有多个解析器
├── parser_model # 模型
├── parser_config # 配置
├── created_by
├── created_at
├── submitted_by
├── submitted_at
├── approved_by
├── approved_at
└── rejection_reason
```

status 需要包含解析流程，外加 failed（失败），还有 purged（审核不通过，需要修改）。based_on_version_id 很重要，这一版不能修改，下一版在这个基础上修改，修改生成一个新的 ParseVersion，状态是未通过。初始版本默认 v0，不修改作为兜底。

文件目录：

```bash
documents/{document_id}/parses/{parse_version_no}/parsed.md
documents/{document_id}/parses/{parse_version_no}/assets/...
```

### IndexGeneration

解析审核通过，就是一个可用文件了。这里还会有一步，同一个文件，可以不同的切片配置，比如切换模型，更换父子块大小。需要一个 IndexGeneration 概念，把切片结果挂在这个对象下面。

```bash
IndexGeneration
├── id
├── document_id
├── parse_version_id
├── status
├── chunking_config # 切片配置
├── embedding_model # embedding 模型
├── child_count
├── created_at
└── published_at
```

切片完成后，IndexGeneration 应该更新父级，修改库里子块搜索可达性。
