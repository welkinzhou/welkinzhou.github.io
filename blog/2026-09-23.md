[前面](./2026-09-03.md)建立的 Golden Set 用于判断问答质量。改检索、Agent 图或解析流程时，我还需要一条不依赖真实模型的工程检查入口，确认日常修改没有破坏格式、类型和已有测试。这里的离线基线回答的是“工程检查能否重复运行”，与 Golden Set 的回答质量评测各自覆盖不同问题。

## 工程回归

一次后端测试失败来自 tiktoken 下载词表时的 DNS，而不是切片逻辑。把测试所需的 tokenizer 资源固定在仓库，并让普通测试禁止真实网络连接后，离线运行才有可重复的基线。后端统一跑 Ruff、格式检查、Mypy 和非集成测试；前端跑测试、lint、类型检查与构建。CI 用锁文件安装依赖，保存版本和测试报告。

项目把后端静态检查、非集成测试和前端检查串在 `quality` 目标里，本地通过统一入口运行：

```bash
make quality
```

`quality-backend` 依次运行 Ruff 检查、格式检查、Mypy 和带覆盖率报告的非集成 pytest；`quality-frontend` 运行 lint、类型检查、Vitest 和构建。CI 按锁文件安装依赖。词表资源放在测试夹具里，避免切片测试因临时联网失败；普通测试还会拦住意外网络调用。这样一处检索参数改动至少不会顺带破坏类型、前端构建或既有单元行为。

这条离线机制由 pytest 自动 fixture 落实：tokenizer 词表从压缩 fixture 解开，校验 SHA-256 后写入独立缓存；普通测试则替换 socket 连接和 DNS 解析入口，只有显式标记为 `integration` 的测试跳过拦截。实现要点如下，省略临时目录及 pytest fixture 声明：

```python
content = gzip.decompress(fixture_path.read_bytes())
assert sha256(content).hexdigest() == expected_hash
cache_dir.joinpath(cache_key).write_bytes(content)

if not is_integration_test:
    monkeypatch.setattr(socket.socket, "connect", denied)
    monkeypatch.setattr(socket.socket, "connect_ex", denied)
    monkeypatch.setattr(socket, "getaddrinfo", denied)
```

因此测试仍使用真实 tokenizer 词表和 token ID，只是阻止它在首次取编码时访问网络下载；缺失或校验失败会报错，不会静默跳过。

这批检查解决的是“相同代码能否稳定通过工程门槛”，不是“RAG 回答是否正确”。固定词表也只是让切片测试不依赖临时下载，不能代替真实中文检索验证。

## 验证范围

当时本地非集成后端为 370 项通过，前端为 19 项通过；远程 CI 的首次运行尚未验证。RAGAS、真实模型、浏览器全流程和负载测试也不在这条离线基线里。把这些结果混成“系统已经验收”，后续看到线上差异就不知道该从哪一层查。

工程基线之外，仓库还提供真实服务集成测试入口：

```bash
make test-integration
```

该目标调用 pytest；由集成测试中的 Testcontainers fixtures 按用例启动并回收容器，例如 PostgreSQL、Redis、RabbitMQ、Elasticsearch、Milvus 和 MinIO。它需要 Docker，Makefile 本身负责选择 `integration` 标记用例并生成报告。
