开始节点设计，第一个就是 Memory。Memory 是按照长短期记忆来的，短期记忆负责提供推理上下文，长期记忆用来提供检索信息做补充。如何配置长短期记忆窗口大小，需要匹配使用的模型。这涉及到整个上下文窗口的分配，设计时就要确定上下文窗口结构。

<!-- truncate -->

确定 Memory 节点设计前，要补上之前的技术债。前面的流程，只是完成了入库，还没有和回答匹配起来。来到 Memory 部分，我们被迫要思考，如何设计上下文窗口、如何切片等。这些是真切能影响到召回效率，从而影响到回答的准确性。

## 上下文设计

原始的设计，会在上下文无脑堆聊天记录，超出就截断或者总结。随着系统越来越成熟，现在的上下文设计精致了很多。大概可以分成胰以下：

| 记忆类型 | 存储方式                      | 请求时是否全部发送 | 建议                               |
| -------- | ----------------------------- | ------------------ | ---------------------------------- |
| 系统指令 | 系统角色与规则                | 否                 | 按照所需 tool、skill 生成          |
| 当前轮   | Prompt                        | 是                 | 当前用户输入                       |
| 短期记忆 | 最近聊天（按 Token 滑动窗口） | 是                 | 按照上下文设置合适大小             |
| 会话摘要 | LLM 自动总结                  | 是                 | 始终携带一份精炼摘要（几百 Token） |
| 长期记忆 | 向量数据库                    | 否                 | mem0 召回                          |
| 知识库   | RAG                           | 否                 | 根据问题检索相关文档               |

谈一下这种设计的逻辑。无脑堆上下文，会面临以下问题。用户不喜欢新开对话，反复在一个对话中问答。历史对话中，充斥着无关信息，真正重要的只有最近的对话信息。超出上下文窗口，做总结真正重要的信息被稀释。如果做截断，原来的信息就完全丢失了。

当前设计中，短期记忆保存最近几条聊天记录，可以补全所需上下文。对话中，通常需要专注的也就是当前话题。为了避免用户询问之前发生的情况时，信息丢失，我们把用户的对话记录完整保存在长期记忆中。每次对话，从数据库检索匹配相关内容召回。比如，用户几周前处理了一个类似问题，今天又复现了。如果不保存完整历史数据，重新询问就需要重新定位，有了历史数据，检索成功就可以直接返回方案。

知识库召回的准确性，直接影响回答准确率。切片小一点，几百 token，有利于语义聚合，方便检索。但是切的太小，文档变得细碎，不利于 llm 理解。现行方案中，常用父子块方式管理。父块按照文档结构切割，内容更多。一本书章节的主题相同，章节中每块内容阐述一个相同信息。回答时，如果我们能把这些完整信息块发送给 llm，得到的回答就会完整。单个字块要小一点，这样语义匹配更准确。比如说，一个做菜文章，可能涉及到选材、处理、制作等部分，如果全放在一个块，只能知道这是一个菜谱。如果我询问如何选材，就没办法精准匹配，主题太多就会四不像。还是这个问题，如果是父子块，检索使用子块（更准确），生成传递父块（信息更完整）。同样的问题，我们就能检索到不同菜谱子块中选材信息，再根据子块联系到父块，最终生成结果就会是，选材主要看....，根据你的不同需要，你可以选择：炒菜....，煮火锅....。这样的回答就会更合理。

## 长短记忆

**短期记忆**通常使用 Redis。Redis 是一个高性能的**键值型内存数据库**，支持 TTL，是后端开发中最常用的缓存中间件之一。我们从两个维度显示短期记忆，一个是对话轮次，另一个是 token。这样一个 `ShortMemoryRepository` 就需要 TTL、token 预算限制、对话轮次限制。

```python
class ShortMemoryRepository:
    """Redis 短时记忆，滑动窗口。

    配置以「对话轮数」计（1 轮 = 1 条用户消息 + 1 条助手消息）；
    Redis LIST 存的是单条 ``HumanMessage`` / ``AIMessage``，条数上限为
    ``max_turns * 2``。
    """

    def __init__(
        self,
        redis: Redis,
        settings: Settings,
        counter: TokenCounter | None = None,
    ) -> None:
        self._redis = redis
        self._max_turns = settings.short_memory_max_turns
        self._token_budget = settings.short_memory_token_budget
        self._ttl = settings.short_memory_ttl_seconds
        self._counter = counter or get_token_counter(settings)

    @property
    def max_messages(self) -> int:
        return self._max_turns * 2

    @property
    def token_budget(self) -> int:
        return self._token_budget

    @staticmethod
    def _key(conversation_id: UUID) -> str:
        return f"chat:history:{conversation_id}"

    def _trim_to_budget(self, messages: list[BaseMessage]) -> list[BaseMessage]:
        """根据窗口限制，计算保留的消息列表。"""
        if not messages:
            return []
        # 强制截断消息
        capped = messages[-self.max_messages :]
        kept_rev: list[BaseMessage] = []
        # 累计已用 token 数
        used = 0
        # 从后往前遍历，保留消息
        for message in reversed(capped):
            cost = self._counter.count_message(message)
            # 如果已用 token 数超过预算，则停止保留
            if kept_rev and used + cost > self._token_budget:
                break
            if not kept_rev and cost > self._token_budget:
                # 单条消息超过预算，则直接返回
                return [message]
            kept_rev.append(message)
            used += cost
        return list(reversed(kept_rev))

    async def add_messages(
        self, conversation_id: UUID, messages: list[BaseMessage]
    ) -> None:
        """添加消息并根据窗口限制截断。"""
        if not messages:
            return
        existing = await self.get_messages(conversation_id)
        await self.replace_messages(conversation_id, [*existing, *messages])

    async def replace_messages(
        self, conversation_id: UUID, messages: list[BaseMessage]
    ) -> None:
        """替换 Redis LIST 消息，并刷新 TTL。"""
        key = self._key(conversation_id)
        # 根据窗口限制截断消息
        window = self._trim_to_budget(messages)
        # 创建 Redis 管道，用于批量操作
        pipe = self._redis.pipeline()
        # 删除原有数据
        pipe.delete(key)
        # 如果消息列表不为空，则将消息列表转换为 JSON 字符串，并添加到 Redis LIST
        if window:
            # 将消息列表转换为 JSON 字符串
            payloads = [
                json.dumps(item, ensure_ascii=False)
                for item in messages_to_dict(window)
            ]
            pipe.rpush(key, *payloads)
            # 刷新 TTL
            pipe.expire(key, self._ttl)
        await pipe.execute()

    async def add_user_message(self, conversation_id: UUID, content: str) -> None:
        await self.add_messages(conversation_id, [HumanMessage(content=content)])

    async def add_ai_message(self, conversation_id: UUID, content: str) -> None:
        await self.add_messages(conversation_id, [AIMessage(content=content)])

    async def get_messages(self, conversation_id: UUID) -> list[BaseMessage]:
        raw_items = await self._redis.lrange(self._key(conversation_id), 0, -1)
        if not raw_items:
            return []
        return messages_from_dict([json.loads(raw) for raw in raw_items])
    
    async def clear(self, conversation_id: UUID) -> None:
        await self._redis.delete(self._key(conversation_id))
```

逻辑不复杂，每次添加消息，把新消息加进队列进行截断。需要注意的是，不是这里增加了截断，请求时就不用处理了。存在单条消息就超过上限的情况，这种情况不能删除，删除会导致对话上下文丢失。在真正发出请求时，还需要做一层处理，保证不超出上下文窗口。同样也不能因为后续还要处理，就认为当前操作没有意义。单个消息超出限制只是极端情况，滑动窗口能在大部分情况下保证对话情景完整。后续必须要做截断或者总结，都是无奈之举，这些操作都会导致信息丢失。

**长期记忆**使用 `Mem0`，它是当前比较流行的方案。长期记忆本质上也是一个 RAG，根据用户的问题，匹配相关内容。Mem0 会自动提取有用的信息，不断的更新用户信息，把这些信息写入向量库，在用到相关画像时返回。

```bash
             用户
              │
              ▼
      LLM（GPT/Qwen）
              │
    ┌─────────┴─────────┐
    │                   │
   当前对话(Context)      Mem0
                            │
          ┌─────────────────┼─────────────────┐
          │                 │                 │
      提取事实          更新旧事实        检索相关事实
          │                 │                 │
          └─────────────────┼─────────────────┘
                            ▼
                     Vector DB + Metadata
```
使用比较简单。Mem0 会根据用户标识，更新相关信息。

```python
from mem0 import Memory

memory = Memory()

messages = [
    {
        "role": "user",
        "content": "我叫w，我喜欢吃炒菜。"
    },
    {
        "role": "assistant",
        "content": "好的，我记住了。"
    }
]
# 添加记忆
memory.add(
    messages,
    user_id="user1"
)
# 查找相关记忆
result = memory.search(
    "我喜欢吃什么？",
    user_id="user1"
)

# 返回结构如下
{
    "results":[
        {
            "memory":"用户喜欢吃炒菜",
            "score":0.95
        }
    ]
}
```

Mem0 开源版本需要自己配置服务地址，包括向量数据库、LLM 和 Embedding 模型。按照下面示例配置即可：

```python
memory = Memory.from_config(
    {
        "vector_store": {
            "provider": "milvus",
            "config": {
                "url": self._settings.milvus_uri,
                "collection_name": "welkin_long_memory",
                "embedding_model_dims": self._settings.embedding_dim,
            },
        },
        "llm": {
            "provider": "openai",
            "config": {
                "model": self._settings.llm_model,
                "openai_base_url": self._settings.llm_base_url,
                "api_key": self._settings.llm_api_key,
            },
        },
        "embedder": {
            "provider": "openai",
            "config": {
                "model": self._settings.embedding_model,
                "openai_base_url": self._settings.embedding_base_url,
                "api_key": self._settings.embedding_api_key,
            },
        },
    }
)
```
