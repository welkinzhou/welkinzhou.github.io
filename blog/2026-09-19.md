[最初的聊天图](./2026-08-05.md)按 Memory、意图、检索、回答的顺序走，适合“查一段资料再回答”。例如用户要“查产品说明，再核对最近公开信息，最后起草邮件”，后续任务需要前面查到的资料，写死分支就难以表达依赖。我把它改成一个 Supervisor 加几个专业子图，让父图根据已完成的任务继续安排工作。

<!-- truncate -->

## Supervisor

Supervisor 每次只决定委派、回答或请求澄清。Web 子图查外部信息，Knowledge 子图查用户有权限的知识库，Action 子图处理需要执行的动作；它们完成后把结果交回父图的 `collect`，再由 Supervisor 决定是否继续。为了让依赖可检查，委派任务带唯一 ID、依赖任务 ID、证据 ID 和工具额度：

```python
# 示意：省略 Pydantic 校验和权限检查，字段对应 TaskSpec / RunBudget。
task = {
    "id": "public_info",
    "agent_id": "web",
    "dependencies": ["product_docs"],  # 只能引用已完成任务
    "evidence_ids": ["evidence-1"],
    "tools": ["web_search"],
    "max_tool_calls": 2,
}
budget = {"max_delegations": 6, "max_tool_calls": 16, "timeout_seconds": 180}
```

`product_docs` 任务完成后，Web 才能依赖它；如果前置任务失败，补查应作为独立任务，而不是假装依赖已经满足。实际派发前还会检查任务 ID、Agent 能力、证据和剩余预算。任务完成后由父图统一收集结果，最终只有 Response 负责写给用户的正文，避免多个 Agent 各说一段、互相覆盖。

父图的连接关系可以从这几条边看出来，省略了节点内部执行代码：

```python
graph.add_edge("prepare", "supervisor")
graph.add_conditional_edges("supervisor", after_supervisor, ["dispatch", "response"])
graph.add_conditional_edges("dispatch", selected_agent, ["web", "knowledge", "action"])
graph.add_edge("web", "collect")
graph.add_edge("knowledge", "collect")
graph.add_conditional_edges("action", after_worker, ["collect", "suspend"])
graph.add_edge("collect", "supervisor")
graph.add_edge("response", "persist")
graph.add_edge("persist", "title")
```

`collect → supervisor` 形成循环，专业子图执行完还能继续规划；Action 可在需要用户确认时转到 `suspend`，结束这一轮并等待用户恢复。`response → persist → title` 只在收尾时顺序执行，避免持久化和标题更新争用同一个数据库会话。

委派不是把一份长聊天记录随手转发。子图只拿到完成任务需要的证据、调用记录和可用工具额度；父图保留完整运行状态，并在收集结果后更新预算。计划校验失败只给一次修正机会，超过委派或工具预算后要收尾并说明未完成事项。

例如“根据产品说明和最近公开信息写一封邮件”，Knowledge 的检索结果、Web 的外部信息和 Action 的发信动作有先后依赖。Action 不能凭模型口头说“前面查过了”就执行；父图要在运行记录里找到完成状态和证据，再派发给相应子图。发信仍会暂停等待用户确认。

## 运行预算

当前默认最多 6 次委派、16 次工具调用、180 秒。父图在派发前核对依赖、委派额度和剩余工具额度；到达硬上限后强制结束规划，交给 Response 说明未完成事项。核心判断可简化为：

```python
# 伪代码：省略结构化结果构造和可用工具权限检查。
completed = {result.task_id for result in run.results if result.status == "completed"}
if not set(task.dependencies) <= completed:
    raise ValueError("task dependencies are not completed")
remaining_calls = run.budget.max_tool_calls - run.budget.tool_calls
if (run.budget.delegations >= run.budget.max_delegations
        or run.budget.tool_calls >= run.budget.max_tool_calls):
    decision = respond_using_existing_evidence()
else:
    worker_tool_limit = min(task.max_tool_calls, remaining_calls)
```

`worker_tool_limit` 是任务自身额度和本轮剩余额度的较小值；达到委派或工具调用上限后，Supervisor 不再规划新任务，而是让 Response 根据已有证据收尾并说明缺口。这些计数存在父图的服务端运行状态中，模型不能调大上限。写操作在 Action 子图中仍会暂停等待确认，暂停的等待时间不计入这一轮执行时限。

这次升级保留了 RAG 的检索链路，但把“什么时候检索、还要不要查别的资料”交给有约束的决策循环。检索命中并不自动成为可信结论，Response 还要看返回的证据是否足够回答。
