## 审核与构建

源文件审核通过才开始解析；解析结果先到待审，人工确认后才构建索引。构建出的 `ready` 索引代仍不可检索，发布才切换可见性。检索还会核对文档当前发布代的指针，不能只看 ES 或 Milvus 里的布尔标记。

索引构建时，子块先写入两端，标记为未发布。向量化只接收子块正文，标题留在 ES 的独立字段：

```python
vectors = await embedding_provider.aembed_documents(
    [child.content for child in children]
)
await milvus_repo.upsert_chunks(children, vectors)
await es_repo.bulk_upsert(children)
```

这里是构建执行器的关键步骤。它写出了可审核的新代，但不会让检索立刻看到新内容。否则管理员还没发布，聊天已经开始引用待审核版本。

这个区分对重建尤其重要。已发布文档可以准备新的解析版本和索引代，旧版在新代准备期间继续服务。当前流程要求先下架旧代，再发布新代，权威指针始终只指向一代。下架先让权威查询排除该代，再清理两端索引标记；清理历史代则只允许处理非当前的稳定代。

发布控制的是整条可见性链路，不是只把向量写进去。下面是状态和指针先后关系的流程伪代码；外部索引更新与 PostgreSQL 指针更新分开执行：

```text
审核 ParseVersion 通过
  -> 创建 IndexGeneration，构建父子块
  -> 写入 ES/Milvus（is_published = false）并标记 ready
  -> 管理员请求发布
  -> 分别更新 ES、Milvus 可见标记，逐端校验更新数 == child_count
  -> 短事务：确认文档没有其他当前代，同时写入 current_index_generation_id 并标记本代 published
```

若是替换当前版本，先完成旧代下架并清空当前指针，再发布新代。数据库事务不能涵盖 ES 和 Milvus；外部更新成功后才提交短事务指针。任一步失败都需要保留任务状态与原因，供幂等重试或人工处理。

## 索引代切换

切换外部可见性时，同一代分别更新 ES 和 Milvus，并用 `child_count` 校验两端更新数量：

```python
published = work_item.action == PublicationAction.PUBLISH
await es_repo.set_generation_published(
    work_item.index_generation_id,
    tenant_id=work_item.tenant_id,
    published=published,
    expected_count=work_item.child_count,
)
await milvus_repo.set_generation_published(
    work_item.index_generation_id,
    tenant_id=work_item.tenant_id,
    published=published,
    expected_count=work_item.child_count,
)
```

这段只处理外部索引。数据库里的当前代指针另由发布流程在短事务中提交，所以一次任务是否完成，不能只看某一端的 `is_published`。

解析和索引任务在数据库提交后投递，待处理任务由定时扫描补投。但正在解析或切片的任务若进程崩溃，自动租约恢复还没做。这是当前发布链路的边界，不能因为有重投就说所有失败都能自动恢复。
