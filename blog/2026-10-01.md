Golden Set 要经过生成、审核和正式打分。设想一轮有 50 道题的评测跑到第 30 题时服务中断；若整批重新检索和生成，前 30 题会重复花费时间，还可能因为模型输出变化把两次结果混在一起。因此评测运行需要保存逐样本预测，让中断恢复时继续补齐同一轮。

## 逐题预测

评测会先筛出有参考答案、已通过审核的样本。每完成一题就保存检索上下文、chunk ID 和生成答案，并以 `sample_id` 作为键。比如某次运行已经保存了 `s-01` 到 `s-30`，恢复时只对缺失的样本调用检索和生成，补齐后再对同一批预测计算四项指标。只有开始新的对比实验时才新建 Run。

评测服务用 `sample_id` 对齐已经落库的预测。关键循环省略了日志，保留续跑判断：

```python
done = {item.sample_id: item for item in existing_predictions}
predictions = []
for sample in scorable:
    cached = done.get(sample.sample_id)
    if cached is not None:
        predictions.append(cached)
        continue
    prediction = await self._predict(sample, tenant_id=tenant_id, kb_id=kb_id)
    predictions.append(prediction)
    if on_prediction is not None:
        await on_prediction(prediction)
```

`on_prediction` 把每题结果及时保存，下一次恢复才能找到 `cached`。如果只在整批结束时写一次报告，中间失败仍要从头检索和生成。

运行记录把实验身份和逐题检查点放在一起。结构示意只列出相关字段；`predictions_json` 中每条预测保存问题、答案、参考答案、检索上下文和命中的 chunk ID：

```json
{
  "set_id": "评测集 ID",
  "status": "failed",
  "generate_model": "回答模型名称",
  "judge_model": "裁判模型名称",
  "predictions_json": [
    {
      "sample_id": "s-01",
      "question": "差旅报销需要哪些材料？",
      "answer": "发票和申请单。",
      "reference": "发票和申请单。",
      "retrieved_contexts": ["报销需发票与申请单。"],
      "retrieved_chunk_ids": ["parent-17"]
    }
  ]
}
```

`status` 是这次 Run 的整体状态；`sample_id` 是恢复时对齐预测与题目的键。恢复时仍使用同一个 Run 的 `set_id` 和模型配置，只把尚未保存的样本补进 `predictions_json`。

这里要分清续跑和新实验。运行中断后复用已完成预测，是为了补完同一次实验；改了检索参数、模型或评测集后，输入条件已经变化，必须创建新 Run 并重新检索、生成，不能拿旧预测给新配置打分。Run 标识的是一轮实验的配置和结果，样本预测是这轮实验的逐题检查点。

## 结果回溯

历史记录不只存一行均分，还保留逐题结果，方便看是哪类问题退化。单题记录至少要能关联 `sample_id`、检索上下文、回答和指标分数；评测集、索引发布代、生成模型与裁判配置则说明这轮分数对应什么条件。Langfuse 可接收对应的样本与分数，但数据库里的评测运行仍是本地页面展示的来源。RAGAS 四项评分有缺失或裁判异常时，需要检查有效样本，而不能只看一条平均线。

这套续跑解决了评测任务的中断成本。它不证明模型结果稳定；做优化比较时，问题集、发布代、模型和裁判配置还要固定。
