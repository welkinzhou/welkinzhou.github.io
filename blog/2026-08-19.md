## 文档处理方案

文档处理要解决两个问题：按原有层级完整还原文档，让 LLM 准确找到需要的内容。前者保存标题、正文和章节之间的关系，后者为检索生成语义集中的块。

完整还原文档有实际用途。回答时要返回原文，检索命中段落 A 的一部分，只返回这一小段，用户可能看不懂。我们需要根据文档结构找到它所属的段落、章节，把理解这段话需要的内容一起返回。用户后续针对某个片段展开追问，也可以沿着原有结构继续查找证据。

保存文档结构不受检索切片的字数预算限制，交给 LLM 的上下文却有长度限制。我们要在有限的上下文中提供尽量完整的信息，不能把保存原文和构造上下文当成同一件事。严格按字符长度切割，会把句子和论述切碎，缺少前后文，LLM 也不容易理解。

我先完整还原文档结构，再生成检索用的语义块。检索块保留与原文的关联，命中后才能回到原文补充上下文。

以下面结构为例：

```markdown
# 第一章 RAG

这是第一章介绍。

## 1.1 RAG 是什么

RAG 是……

## 1.2 RAG 架构

RAG 包含……

### 1.2.1 Retriever

Retriever......

### 1.2.2 Generator

Generator......

### 1.2.3 Reranker

Reranker......
```

按长度硬切，单独拿到一个 chunk，看不出它在讲哪部分：

```markdown
// chunk 1
# 第一章 RAG
这是第一章
// chunk 2
介绍。
## 1.1 RAG 是什么
// chunk 2
是什么
RAG 是……
```

按标题切也要处理边界：章节有长有短，一级标题下还包含二、三级标题，不能把每个标题都当成独立、等长的块。我先用树保存这些从属关系，再处理检索切片的大小，避免为了凑长度改变原文结构。

### 自然结构还原

之前习惯按聊天来想文档，忽略了标题的作用。聊天可以讲完 A、B、C，再回头讲 A：第 1、4 段都在说 A，中间两段分别说 B、C，话题的层级是隐含的。

文章通过标题明确组织内容。正文从属于当前标题，二、三级标题也从属于上级标题。还原一个章节，既要拿到它自己的正文，也要按顺序找到子章节，不能只把散落的段落拼在一起。

我用三个类描述文档：`Document` 代表文件，`Section` 保存章节树，`Block` 保存 Markdown 元素。

#### Document

Document 关联原文件，Section 保存解析内容。原文件仍放在 MinIO，重建文档时按原文顺序拼接各个 section 的标题和正文，子章节沿树继续展开。

```python
@dataclass
class Document:
    id: str
    # 文档基本信息
    title: str
    filename: str
    # 原始文件信息
    file_type: str
    source_object_key: str
    # 解析后的 Markdown
    parsed_object_key: str | None = None
    # 文档结构
    sections: list["Section"] = field(default_factory=list)
    # 文档级元数据
    metadata: dict[str, Any] = field(default_factory=dict)
```

#### Section

Section 保存当前标题和正文，子 Section 单独挂在树里，不重复放进正文。这里保留完整内容，不限制长度。

Section 类型如下：

```python
@dataclass
class Section:
    id: str
    document_id: str
    # 层级
    level: int
    # 标题
    title: str
    parent_id: str | None = None
    children: list["Section"] = field(default_factory=list)
    section_path: list[str] = field(default_factory=list)
    blocks: list[Block] = field(default_factory=list)
    metadata: dict[str, Any] = field(default_factory=dict)
```

section_path 标记章节路径，让 LLM 看出当前内容属于哪个主题，也方便后续 search 工具定位原文、沿章节补充证据。level 用来记录标题层级，解析出错时可以手动纠正。

#### Block

类型如下：

```python
from dataclasses import dataclass, field
from enum import Enum
from typing import Any


class BlockType(str, Enum):
    PARAGRAPH = "paragraph"
    LIST = "list"
    TABLE = "table"
    IMAGE = "image"
    CODE = "code"
    FORMULA = "formula"
    QUOTE = "quote"


@dataclass
class Block:
    id: str
    # 内容类型
    type: BlockType
    # 当前 Block 的原始/标准化内容
    content: str
    # 来源定位
    page_start: int | None = None
    page_end: int | None = None
    # 在原始解析结果中的位置
    index: int = 0
    # 类型相关的扩展信息
    metadata: dict[str, Any] = field(default_factory=dict)
```

### 语义块

子块用来做语义检索，父块提供更完整的上下文。块太大，主题分散，不容易准确匹配；块太小，又容易缺少理解所需的信息。具体例子见[《RAG 系统五》](./2026-08-06.md#上下文设计)。这里继续解决生成方式：从 section 树构造父块，再切子块。

单个 section 足够大，就形成父块；内容不足，就按文档顺序合并。比如父块预算 3000，h1 正文 500，下面两个 h2 各 1200，合起来 2900。

直接沿标题树递归合并，会遇到 `h1 → h2 → h3 + h3` 的情况：加到第二个 h3 才发现超预算，还得退回上一层重新决定边界。我更愿意先展平 section，按文档顺序处理大小，同时保留它们原来的层级关系。

展平后的文本保留结构信息，用来构造父块。类型如下：

```python
class ChunkType(str, Enum):
    PARENT = "parent"
    CHILD = "child"


@dataclass
class ParentChunk:
    id: str
    document_id: str

    type: ChunkType = ChunkType.PARENT

    content: str = ""

    section_ids: list[str] = field(default_factory=list)
    section_path: list[str] = field(default_factory=list)

    page_start: int | None = None
    page_end: int | None = None

    token_count: int = 0

    metadata: dict[str, Any] = field(default_factory=dict)
    
@dataclass
class ChildChunk:
    id: str
    parent_id: str
    document_id: str

    type: ChunkType = ChunkType.CHILD

    content: str = ""

    section_id: str | None = None
    section_path: list[str] = field(default_factory=list)

    page_start: int | None = None
    page_end: int | None = None

    token_count: int = 0

    metadata: dict[str, Any] = field(default_factory=dict)
```

父块预算 3000、子块预算 500，展平结果如下：

```python
Section 1 # 300
Section 1-1 # 1200
Section 1-2 # 1400
Section 1-3 # 1400
Section 2 # 300
```

`300 + 1200 + 1400 = 2900`，前三个 section 合成父块，1-3 另起一块。

很短的标题不必固定为切割边界，避免切得太碎。

```
H1
 └── Parent 永远不能跨

H2
 └── 尽量不要跨，但必要时可以

H3/H4
 └── 尽量合并
```

父块边界确定后，拼接对应 section 的内容，再切子块。父块用 section_ids 关联原章节，子块用 parent_id 关联父块，并保留所属章节和位置。切片只是为检索组织内容，不能切断它和原文的关系，后续才能按命中位置返回完整内容、继续追问。
