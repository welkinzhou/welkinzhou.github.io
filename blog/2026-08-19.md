# 文档处理方案

文档如何处理，包括了两部分内容。一是，如何层次清晰地完整还原出文档内容。二是，如何让 LLM 准确找到需要内容。这是两个截然不同的事情，混在一起出来就会很乱。为什么不能混在一起？文档分割是没有字数限制的，但是上下文有限制。我们需要在有长度限制情况下，给出更全面的信息。严格按照字符长度限制切割，会把文档切的很碎，不方便 LLM 理解。

以下面结构为例：

```markdown
# 第一章 RAG

这是第一章介绍。

## 1.1 RAG 是什么

RAG 是……

## 1.2 RAG 架构

RAG 包含……

### 1.2.1 Retriever

Retriever......

### 1.2.2 Generator

Generator......

### 1.2.3 Reranker

Reranker......
```

按照长度切，可能变成这样，单独拿到一个 chunk，根本不知道说什么：

```markdown
// chunk 1
# 第一章 RAG
这是第一章
// chunk 2
介绍。
## 1.1 RAG 是什么
// chunk 2
是什么
RAG 是……
```

如果按照格式分割，如何确定块的边界。章节中有的长有的短，标题还存在包含关系，怎么处理。两部分混在一起考虑，会考虑不清，所以我们分成两部分考虑。先还原文档结构，再考虑语义切割。我们把用到的类分成两部分，一是文档自然结构，二是语义块。

## 自然结构还原

碎片化的思考，让我自己陷入一个误区。日常对话是很随意的，结构是松散的。文章不是这样，文章应该有清晰的结构。比如，有 A、B、C 三个论点，日常生活中，我们可能在聊完 A、B、C 后，折回去继续讨论 A。也就是说，有 1-4 个片段，1、4 关于 A，2 关于 B，3关于 C。

文章不是这样，因为文章要有标题。日常对话中，标题是隐藏的，使我陷入话题绕回去的陷阱。文章可以分为标题和内容两部分，内容从属于标题。标题是 RAG，整篇文章应该都是关于 RAG。一级标题下的内容，都属于一级标题，包括二三级标题。

这样我们只需要3个类就能描述清整个文档。1. `Document` 表明整个文档。2. `Section` 文本块，通过树形嵌套，存储整个文本内容。3. `Block` md 元素。

### Document

Document 代表文件。在项目中，文件原数据保存在 MinIO 中。重建文件时，只需要把所有 section 拼接在一起。

```python
@dataclass
class Document:
    id: str
    # 文档基本信息
    title: str
    filename: str
    # 原始文件信息
    file_type: str
    source_object_key: str
    # 解析后的 Markdown
    parsed_object_key: str | None = None
    # 文档结构
    sections: list["Section"] = field(default_factory=list)
    # 文档级元数据
    metadata: dict[str, Any] = field(default_factory=dict)
```

### Section

Section 才是具体存放内容的地方。Section 需要标题和内容，为了方便构建树形关系，内容区不应该包含子 Section。Section 只需要保存文档内容，不需要考虑大小。

Section 类型如下：

```python
@dataclass
class Section:
    id: str
    document_id: str
    # 层级
    level: int
    # 标题
    title: str
    parent_id: str | None = None
    children: list["Section"] = field(default_factory=list)
    section_path: list[str] = field(default_factory=list)
    blocks: list[Block] = field(default_factory=list)
    metadata: dict[str, Any] = field(default_factory=dict)
```

section_path 很重要，可以帮助快速理解内容大意。后续如果做 searh 工具，可以帮助 LLM 快速定位。level 旨在解析出错问题时，手动纠正层级。

## 语义块

语义切割是为了向量化搜索。如果切块太大，语义很散，不方便找到想要内容。切块太小，又会缺失上下文。所以现在使用父子块，子块用来做语义搜索，父块传递给 LLM 提供更完整的上下文。接下来要考虑我们已经有了 section，如何划分父子块。

简单情况就是，一个块内容够大，直接作为父块，并切割出子块。当父块内容不够大时候，就需要向下查找、合并。比如父块3000，h1 自身只有 500，下面还有两个 h2 分别 1200，加起来 2900 差不多，这样父块就是 `h1 + h2 + h2`。问题就是怎么合并？直接处理会出现递归，`h1 -> h2 -> h3 + h3`，到第二个 h3 发现超了，就要退回去，这样肯定不行。

我们需要先把 section 展平，这就相当于把文档重建成文本，并附上了结构。这样先构造父块，再在父块中分割子块。类型如下：

```python
class ChunkType(str, Enum):
    PARENT = "parent"
    CHILD = "child"


@dataclass
class ParentChunk:
    id: str
    document_id: str

    type: ChunkType = ChunkType.PARENT

    content: str = ""

    section_ids: list[str] = field(default_factory=list)
    section_path: list[str] = field(default_factory=list)

    page_start: int | None = None
    page_end: int | None = None

    token_count: int = 0

    metadata: dict[str, Any] = field(default_factory=dict)
    
@dataclass
class ChildChunk:
    id: str
    parent_id: str
    document_id: str

    type: ChunkType = ChunkType.CHILD

    content: str = ""

    section_id: str | None = None
    section_path: list[str] = field(default_factory=list)

    page_start: int | None = None
    page_end: int | None = None

    token_count: int = 0

    metadata: dict[str, Any] = field(default_factory=dict)
```

假设，父块大小要求 3000，子块500，展平后 section 大小如下：

```python
Section 1 # 300
Section 1-1 # 1200
Section 1-2 # 1400
Section 1-3 # 1400
Section 2 # 300
```

`300 + 1200 + 1400 =2,900`，所以前三个 section 就要变成一个父块。1-3 只有就不是 Section 1 了，他自己也要切一个块。

过于小的标题，也没必要作为死边界，不然切的太碎了。

```
H1
 └── Parent 永远不能跨

H2
 └── 尽量不要跨，但必要时可以

H3/H4
 └── 尽量合并
```

难以界定的，主要就是父块。父块界定完成，就是会 sections 内容拼接成字符串，子串只需要做切割即可。
